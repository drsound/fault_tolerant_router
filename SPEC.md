## 1. Context

PolyWAN was called Fault Tolerant Router until version 2.0. Fault Tolerant Router 1.x is a Ruby daemon, written in 2015–2016, that runs on a Linux router with several internet uplinks. It balances new outgoing connections across the healthy uplinks with kernel multipath routing, keeps every connection on the uplink it started on (connection marks plus policy routing), monitors the uplinks by pinging public hosts, supports priority groups and weights, and sends email on state changes. It is IPv4-only, generates iptables rules that the administrator integrates by hand, shells out to `ip` and `ping`, and requires that the main routing table has no default route.

Version 2.0 is a ground-up rewrite in Rust. It keeps the core idea of 1.x (multipath routing for new connections, connection marks for pinning) and brings it up to date with the Linux networking stack of 2026: nftables, netlink, dual-stack IPv4/IPv6, dynamic (DHCP/RA/PPP) uplinks that coexist with the operating system's own default routes, and modern observability. The routing policy database layout changes materially compared to 1.x; behaviour is defined by the invariants of §4.1, not by compatibility with 1.x.

### 1.1 Who it is for

An administrator running a general-purpose Linux distribution (Debian, Ubuntu, Fedora, Arch, Raspberry Pi OS, a virtual machine, …) as a router or firewall with two or more internet uplinks, who does not want to replace it with a router distribution such as OpenWrt (mwan3), OPNsense/pfSense or VyOS. Typical 2026 setups: fibre plus a 5G or Starlink backup; two fibre lines in an office; a metered line used only when the others fail.

### 1.2 Goals

1. Transparent use of all healthy uplinks for new outgoing connections, with weights and priority groups.
2. A connection keeps its uplink for its whole life while that uplink remains usable; inbound connections are answered through the uplink they arrived on (precise contract in §4.1).
3. Fast and reliable failure detection, including "link up but provider disconnected from the internet" and, optionally, "link degraded".
4. IPv4 and IPv6 treated as first-class and independent: an uplink can be healthy for one family and failed for the other.
5. Uplinks with static, DHCP, SLAAC/RA or PPP addressing, without per-type configuration.
6. Zero-friction installation (one static binary, a systemd unit, a managed nftables table) with an alternative for administrators who manage nftables themselves.
7. Observable and scriptable: status API and CLI, Prometheus metrics, event hooks, email.
8. Verifiable behaviour: every functional requirement is covered by automated tests that move real packets through network namespaces, in CI.

### 1.3 Non-goals for 2.0

- Configuring interfaces, addresses, DHCP/DHCPv6/PPP clients, Router Advertisements or DHCPv6 prefix delegation. These remain the job of the operating system (systemd-networkd, ifupdown, NetworkManager, pppd, …). PolyWAN observes them.
- Filtering firewall policy. PolyWAN only marks packets and, optionally, performs source NAT. It never drops or accepts traffic on behalf of the administrator.
- Per-packet load balancing, bandwidth measurement or dynamic weight adjustment.
- IPv6 prefix translation (stateful prefix NAT or NPTv6) and automatic use of delegated prefixes. 2.0 supports IPv6 masquerade, SNAT to a static address, and no NAT (§6).
- IPv6 multihoming without NAT (several provider prefixes advertised to the LAN, with source-address-based routing and prefix deprecation on failure).
- Policies applied to traffic originated by the router itself (§4.5).
- Owning nexthop objects (`ip nexthop`) and using nexthop groups; 2.0 installs inline multipath routes (§4.3) and only resolves single nexthop objects found in discovered routes (FR-DISC-3).
- Supporting hardware or software nftables flow offload of traffic between PolyWAN downlinks and uplinks, including offload of only one direction (§4.8, FR-CT-2).
- Running as a non-root user.
- High availability between two routers (VRRP and similar), a web user interface, platforms other than Linux, internationalisation (1.x issue #5), routing realms (1.x issue #4).

## 2. Terminology

- **Uplink**: an interface connected to an internet provider, identified by a stable numeric `id` and a `name` (§11).
- **Downlink**: an interface connected to an internal network (LAN, DMZ, …) whose traffic is routed through the uplinks.
- **Family**: IPv4 or IPv6. Most state in PolyWAN is tracked per (uplink, family) pair, called a **path**. A path exists only if the uplink's configuration enables that family.
- **Ready**: a path whose interface exists and is up with carrier, has a usable source address (§5.1) and has a usable next hop (a gateway for every IPv6 path and for non-point-to-point IPv4 paths, or a device-only next hop for an IPv4 point-to-point path), and whose installation has not failed (FR-DISC-7).
- **Healthy**: a path whose health state (§5.3) is `up`. Only ready paths can be healthy.
- **Eligible**: a path whose uplink has a `priority` and is not drained (§4.4).
- **Candidate**: a path that is eligible and ready.
- **Active set**: for each family, the paths currently used for new outgoing connections (§4.4).
- **PolyWAN field**: the 8 contiguous bits of the packet/connection mark reserved to PolyWAN (`fwmark_mask`).
- **Artifact**: any object installed by PolyWAN: routing rule, route, nftables table, sysctl value, state file.
- **Main bypass**: the routing of destinations covered by a non-default route in the main table (§4.1, INV-1).

## 3. Platform requirements

- **PLAT-1** Linux kernel 6.1 or later. The daemon MUST check the running kernel version at startup and refuse to start on older kernels. Every kernel error during application MUST be reported with the attempted operation, the errno and the netlink extended acknowledgement message; netlink sockets enable `NETLINK_EXT_ACK`, and when the kernel provides no message (many errors carry only the errno) the report says so. An error is described as a missing feature only after a targeted capability test has established it.
- **PLAT-2** nftables 1.0.6 or later, when the managed firewall mode is used (§7).
- **PLAT-3** Architectures: x86_64, aarch64 and armv7 (Raspberry Pi). Release binaries MUST be statically linked (musl).
- **PLAT-4** systemd is the primary supported service manager; PolyWAN MUST NOT depend on it at runtime (it runs in the foreground and logs to stderr).
- **PLAT-5** PolyWAN runs as root, sandboxed by its systemd unit (§12.4). Running as a non-root user is not supported in 2.0.

## 4. Routing model

### 4.1 Invariants

The design exists to guarantee the following invariants. Every acceptance scenario (§14.3) checks one or more of them. Guarantees depend on the lifecycle phase:

- **Installation** (cold installation of FR-REC-1, warm adoption of FR-REC-8): no guarantee beyond FR-REC-1's statement that traffic follows either the pre-existing routing or PolyWAN's routing; the invariants begin at the end of installation.
- **Active operation**, including reloads, runtime changes and partially applied generations caused by failed kernel operations (FR-REC-5): the invariants hold.
- **Repair** after a third party deletes or alters PolyWAN artifacts: the invariants cannot be guaranteed while the artifacts are missing; they hold again once restored (FR-COEX-3).
- **Cleanup** (FR-REC-4): guarantees end when cleanup starts; routing is handed back to the operating system in the documented order.

The invariants apply only to traffic of a managed family (§4.3) that reaches PolyWAN's rules: the local table (priority 0) and any foreign rule with a priority lower than `rule_priority_base` take precedence by construction (FR-ROUTE-6).

- **INV-1 (main bypass)** Packets whose destination is covered by a non-default route in the main table (connected networks, downlinks, static routes, VPN routes, routes pushed by DHCP option 121) are routed by the main table, bypassing path selection, pinning and policies; the only PolyWAN rules that precede the main bypass are the probe rules (INV-6). This is intentional: it keeps internal and VPN traffic working. A VPN that installs `0.0.0.0/1` + `128.0.0.0/1` therefore overrides PolyWAN for all traffic, by design. Default routes in the main table are never used for traffic that enters PolyWAN's rule sequence. Deployment contract: routes towards downlinks and other internal destinations MUST be in the main table (FR-DISC-8).
- **INV-2 (pinning)** Except where INV-1 applies, a tracked connection that has been assigned a path is routed through that path's table for its whole conntrack lifetime, in both directions, regardless of later changes to health, active set, drain state or policies. If the path is not ready or no longer configured, its packets are rejected with ICMP unreachable rather than moved to another uplink (moving would change the source address and break the connection anyway). Exception: IPv4 packets of router-originated connections bound to an interface may instead be sent on-link through that interface (§4.1.1); they are never moved to another uplink.
- **INV-3 (no leak)** A packet that reaches PolyWAN's rules and is not handled by the main bypass is either routed by a PolyWAN table or rejected by a PolyWAN guard rule; it never reaches a non-PolyWAN routing table, and in particular never uses a default route installed by the operating system. Router-originated traffic bound to an interface is outside this invariant (§4.1.1).
- **INV-4 (new connections)** A new forwarded connection not matched by a policy, and a new router-originated connection bound neither to an uplink address nor to an interface (§4.1.1), is routed only through a member of its family's active set, or rejected with ICMP unreachable if the active set is empty or, transiently, if the balancing route is absent after a failed IPv6 update (FR-ROUTE-2). Probes are excluded (INV-6).
- **INV-5 (inbound symmetry)** Except where INV-1 applies, packets of a connection that arrived on uplink *U* (including replies from downlink hosts after DNAT, and replies from the router itself) leave through *U*, also when *U* is not in the active set or is drained, as long as *U* is ready.
- **INV-6 (probes)** Probe traffic for a path leaves through that path's interface, using that path's next hop and source, whenever the path is ready, regardless of health, active set, drain state, policies and main-table routes.
- **INV-7 (non-interference)** PolyWAN never modifies mark bits outside the PolyWAN field, never deletes or modifies objects it does not own, never adds `drop`/`reject`/`accept` verdicts to nftables, and never changes sysctls other than those listed in §4.6.
- **INV-8 (decoupling)** Notifications, hooks, API clients and metrics scrapes never delay routing decisions.

Continuity is promised only for connections whose path stays ready and keeps the same source address and conntrack entry. Connections on a failed uplink generally break and are re-established by the client on another uplink.

#### 4.1.1 Traffic bound to an interface

Router-originated traffic whose socket is bound to an interface (`SO_BINDTODEVICE`, `IP_UNICAST_IF`/`IPV6_UNICAST_IF`, an `IP_PKTINFO` interface index) is an explicit egress decision of the program: it is exempt from drain like traffic bound to an uplink address (FR-SEL-3), it is excluded from INV-3 and INV-4, and for IPv4 the rejection promised by INV-2 does not apply to it. PolyWAN guarantees only that it never leaves through another interface, and does not guarantee that it reaches its destination (an IPv4 datagram sent on-link on Ethernet is generally lost). Spike S1 established the kernel behaviour on 6.1 and 7.1, which PolyWAN cannot change:

- IPv4: a route lookup constrained to an output interface that fails, whether because of an `unreachable` rule, an `unreachable`/`prohibit`/`blackhole` route or no route, is treated as "destination on-link on that interface" (`ip_route_output_key_hash_rcu`). Guard rules therefore do not terminate such traffic; it can only leave through the bound interface (on Ethernet the router ARPs for the destination; on a point-to-point link the packet is sent to the peer).
- IPv6: an interface-constrained lookup that finds no route fails with `ENETUNREACH`. For connected sockets and unconnected datagrams whose source address is unspecified, the kernel attempts source selection and repeats the lookup. After a failed first lookup, source selection is not restricted to the bound interface and may choose an address of another interface. If the selected address matches the bound path's source rule (B + 500 + id), the second lookup uses that path's table, or its source guard. Otherwise, if no route satisfies the retained interface constraint, the lookup fails with `ENETUNREACH`. Source selection itself can also fail. PolyWAN MUST NOT send this traffic through another interface; successful connectivity is not guaranteed.
- IPv4 connected sockets behave like IPv6: the source chosen by the on-link fallback is used for a second lookup that matches the source rule.

The documentation MUST describe this behaviour.

### 4.2 Marks

- **FR-MARK-1** PolyWAN MUST use only the 8 bits selected by `fwmark_mask` (default `0x00ff0000`, MUST be exactly 8 contiguous bits) of packet and conntrack marks, and MUST preserve all other bits (INV-7).
- **FR-MARK-2** Each uplink has a stable `id` from 1 to 63, set explicitly in the configuration (§11). The **field value** stored in the PolyWAN field encodes a class (2 high bits) and the uplink id (6 low bits); 0 means "no PolyWAN assignment":

  | Class | Field value | Meaning | Stored in |
  |---|---|---|---|
  | path | `id` | connection assigned to the uplink's path | conntrack mark and packet mark |
  | probe | `0x40 + id` | probe traffic of the uplink | packet mark (probe sockets) |
  | policy, fallback balance | `0x80 + id` | new connection matched by a policy targeting the uplink, `fallback = "balance"` | packet mark only |
  | policy, fallback block | `0xc0 + id` | same, `fallback = "block"` | packet mark only |

  The maximum number of uplinks is therefore 63.
- **FR-MARK-3** Field values are placed in the mark by `encode(v) = v << trailing_zeros(fwmark_mask)`. Every routing rule selector and every nftables mark operation MUST use encoded values and the mask (for example, with the default mask, the probe value of uplink 1 is `0x00410000/0x00ff0000`). Writing the PolyWAN field MUST be implemented with constant operations only (`meta mark set meta mark & ~mask | encode(value)`), one rule per value, because combining two variable registers is not available on all supported kernels. Restoration rules (§4.7) MUST exist for all 63 path values, whether configured, retired or never used, so that connections of removed uplinks keep their mark and reach the path guard; assignment rules exist only for configured uplinks.
- **FR-MARK-4** Uplink identity is the pair (`id`, `name`). The binding is persisted in the state directory (§12.3). Reusing an `id` for a different `name`, or changing the `id` of an existing `name`, MUST be rejected while the old binding is recorded. An uplink removed from the configuration keeps its id reserved until the administrator runs `polywan forget-uplink NAME`, whose documentation explains that connections still carrying the old id must be flushed or allowed to expire first; until then they are rejected by the path guard (FR-ROUTE-3).

### 4.3 Routing tables and rules

A family is **managed** when at least one configured uplink enables it. All of PolyWAN's rules, guards and tables exist only for managed families; an IPv4-only installation installs nothing for IPv6. When a reload removes the last path of a family, PolyWAN hands that family back to the operating system with a scoped procedure (FR-REC-9) and emits an event.

For each managed family, PolyWAN owns the routing tables `table_base` to `table_base + 191` (default `table_base = 1000`) and the rule priorities `rule_priority_base` to `rule_priority_base + 699` (default 1000). All PolyWAN rules and routes MUST be installed with the routing protocol number `route_protocol` (default 249). Every PolyWAN table holds at most one route: a usable default route with the fixed metric 100, present only when the table says so below; otherwise the table is empty. Withdrawing a route means deleting it (exact key: table, family, destination `default`, metric 100).

| Table | Purpose | Default route present when |
|---|---|---|
| `table_base` | balancing (new connections) | the active set is non-empty: a multipath route over its members (single nexthop if one member) |
| `table_base + id` | path of uplink `id` | the path is ready, regardless of health: `via <gateway> dev <iface> src <source>` (IPv4 point-to-point: `dev <iface> src <source>`) |
| `table_base + 64 + id` | policies with fallback balance | the path is healthy and the uplink is not drained: same route as the path table |
| `table_base + 128 + id` | policies with fallback block | the path is healthy and the uplink is not drained: same route as the path table |

- **FR-ROUTE-1** Termination is enforced by **guard rules** (routing rules whose action is `unreachable`), not by routes: one guard per mark class gives class-specific fallthrough (policy-balance without copied routes) and a single final guard. Neither a guard rule nor a reject route terminates an IPv4 lookup constrained to an output interface (§4.1.1). A lookup that finds no usable route in a PolyWAN table continues to the next rule and is caught by the guard of its class, or by the final guard (FR-ROUTE-3). The policy-balance class intentionally has no guard: its fallthrough reaches the balancing rule, which implements `fallback = "balance"` without copying routes; no rule between them can match a policy-balance mark, because the block-class rules and guard select another class and the source rules require a zero PolyWAN field.
- **FR-ROUTE-2** The balancing route is an inline multipath route (RTA_MULTIPATH) with each member's configured weight, updated with `NLM_F_REPLACE`. For IPv4 the replacement is a single atomic operation. For IPv6 the kernel replaces the old members with the first new one and then adds the others, so the update is not atomic. The requirement is therefore defined in phases around the **transition boundary**, the first kernel mutation of the update that succeeds:
  - before the boundary (including an update rejected without any mutation), the previously applied route stays in force and new connections use the previous active set;
  - after the boundary, the route contains only members of the target active set, possibly a non-empty subset while the update is in progress or after a partial failure; it is empty only if the target set is empty, except after the IPv6 failure described below;
  - pinned connections are unaffected in every phase;
  - an update is complete when the route equals the target set; until then the status is `degraded`, the failure is reported as `apply_failed` and retried (FR-REC-5);
  - exception for IPv6: if an insertion after the first fails, the kernel deletes the members it has already inserted and reports "multipath route replace failed (check consistency of installed routes)"; the old route is gone and the new one is not installed, so the balancing table is empty although the target set is not. New connections are then rejected by the final guard (INV-4 holds) until the retry succeeds. PolyWAN MUST re-read the table after any failed IPv6 update.

  Spike S1 established on 6.1 and 7.1 that every validation failure (off-link gateway, missing device, member interface down, duplicate member, device-only member) is detected before the first mutation and leaves the previous route in force, that IPv6 add and replace produce a single notification with the complete route, and, from the kernel source (not from an injected failure: the tested kernels lack fault injection), that the intermediate states are non-empty subsets of the target set and that the exception above requires an allocation failure. The duplicate-member and device-only rejections are IPv6 behaviour; IPv4 accepts both. A member whose interface goes down between planning and application makes the whole update fail; the failure is resolved by replanning on the link event.
- **FR-ROUTE-3** Routing rules, per family, at fixed offsets from `rule_priority_base` (B). `encode` is defined in FR-MARK-3; "/class" means the mask `encode(0xc0)`:

  | Priority | Selector | Action | Purpose |
  |---|---|---|---|
  | B + id | `fwmark encode(0x40+id)/mask` | lookup path table | probes (INV-6) |
  | B + 64 | `fwmark encode(0x40)/class` | unreachable | probe guard |
  | B + 100 | (all) | lookup `main`, `suppress_prefixlength 0` | main bypass (INV-1) |
  | B + 200 + id | `fwmark encode(id)/mask` | lookup path table | pinned connections (INV-2, INV-5) |
  | B + 264 | `fwmark encode(2^k)/encode(0xc0 + 2^k)`, k = 0…5 (six rules) | unreachable | path guard: any non-zero path-class value, including retired ids |
  | B + 300 + id | `fwmark encode(0x80+id)/mask` | lookup policy-balance table | policies with fallback balance (falls through to B + 600 when empty) |
  | B + 400 + id | `fwmark encode(0xc0+id)/mask` | lookup policy-block table | policies with fallback block |
  | B + 464 | `fwmark encode(0xc0)/class` | unreachable | policy-block guard |
  | B + 500 + id | `from <address> fwmark 0/mask`, one rule per local address of the path (FR-DISC-2) | lookup path table | router-originated traffic bound to an uplink address, including replies of router services; the zero-field selector keeps policy-marked forwarded traffic out |
  | B + 564 | `from <address> fwmark 0/mask`, one rule per address above | unreachable | source guard |
  | B + 600 | (all) | lookup balancing table | new connections (INV-4) |
  | B + 699 | (all) | unreachable | final guard (INV-3) |

  Lookup rules exist only for configured uplinks; guards exist for every managed family while PolyWAN is installed. All rules are static for a given configuration, except the `from` rules and source guards, which follow the usable addresses. Runtime changes of health, drain and active set are applied only through route replacements and deletions (FR-REC-2).
- **FR-ROUTE-4** PolyWAN MUST NOT delete or modify routes, rules or tables it does not own (INV-7). Default routes installed in the main table by the operating system stay there and are used for discovery (§5.1); because of the final guard they are never used for traffic that enters PolyWAN's rule sequence while PolyWAN is installed.
- **FR-ROUTE-5** PolyWAN MUST set `fib_multipath_hash_policy = 1` (layer 4) for each managed family when `manage_sysctls = true`.
- **FR-ROUTE-6** `rule_priority_base` MUST be at least 1 and the range MUST end below 32766 (the main table rule); the table range MUST NOT include 253–255. Startup MUST fail if any rule in the priority range, or any route in the table range, exists that is not tagged with `route_protocol` (collision with another tool), and MUST fail if the local-table rule at priority 0 is missing. The kernel's VRF rule (action `l3mdev`, protocol `kernel`, priority 1000 by default) is not a collision: it matches only traffic of VRF devices; it is listed in the warning of foreign rules below. Foreign rules with priorities between 1 and `rule_priority_base` precede PolyWAN: startup and `check-config` MUST list them in a warning, and the documentation MUST state that PolyWAN's invariants do not cover traffic they match.

### 4.4 Active set selection

For each family independently, the active set is computed from the candidates (eligible and ready paths) with this decision table:

| Condition | Active set |
|---|---|
| At least one candidate is healthy | healthy candidates of the lowest-numbered priority group among healthy candidates |
| No healthy candidate, at least one candidate, `all_down_policy = "ready"` (default) | candidates of the lowest-numbered priority group among candidates, regardless of health |
| No healthy candidate, at least one candidate, `all_down_policy = "keep"` | previous active set (persisted, §12.3) restricted to current candidates |
| Any other case, or the result above is empty | empty: the balancing table has no route, new connections are rejected by the final guard |

- **FR-SEL-1** Selection MUST follow the table above. Rationale for `ready`: if every check fails at once, the probes themselves may be the problem (for example, the targets are unreachable); still preferring the best priority group avoids spilling onto metered uplinks.
- **FR-SEL-2** An uplink with no `priority` is never a candidate, but its path table, inbound connections, probes and policies keep working.
- **FR-SEL-3** **Drain**: the administrator MAY drain an uplink at runtime (§9). A drained uplink is not eligible: it receives no new forwarded connections, neither through balancing nor through policies (its policy tables become empty, so their fallback applies), and no new unbound router-originated connections. Existing connections, inbound connections (INV-5), probes, and router-originated traffic explicitly bound to one of the uplink's addresses continue: an explicit binding is an administrator decision that drain does not override. Traffic bound to the uplink's interface is likewise exempt from drain, with only the guarantees of §4.1.1. Drain state is persisted in the state directory and survives restarts and upgrades until undrained or until the uplink is removed from the configuration. A drain or undrain request is persisted durably (IMPL-5) before it is applied and before the API acknowledges it; on restart, the persisted intent is applied whatever the kernel state left by a crash. At startup, persisted drain names absent from the configuration are pruned durably before routing changes. On reload, pruning occurs after successful preparation and before commitment of the new configuration; failure to persist it prevents commitment. Rejected reloads retain the previous drain intent. Once committed, removal clears the intent even if subsequent kernel application is partial; re-adding the uplink does not restore its former drain flag.
- **FR-SEL-4** The API MUST refuse to drain the last candidate of a family unless the request sets `force = true`.

### 4.5 Policies

Policies force matching new forwarded connections through a specific uplink, replacing the hand-written iptables examples of 1.x (for example: always send SMTP from the address with the right PTR record; keep a VoIP device on the low-latency line).

- **FR-POL-1** A policy matches new forwarded connections by any combination of: family, input interface (MUST be a downlink), source prefix, destination prefix, L4 protocol, destination port or port range. Policies are evaluated in declaration order; the first match wins.
- **FR-POL-2** A matching connection gets, in the packet mark only, the policy value for its target uplink and fallback (FR-MARK-2). The conntrack mark is assigned the actual egress path after routing (§4.7), so a connection is pinned to whatever uplink its first packet actually used (INV-2), and later policy table changes never move it.
- **FR-POL-3** `fallback = "balance"` (default): while the target path is not healthy or the uplink is drained, matching new connections are balanced over the active set. `fallback = "block"`: they are rejected with ICMP unreachable.
- **FR-POL-4** Policies do not apply to traffic originated by the router itself in 2.0. Such traffic follows FR-ROUTE-3 (balancing or `from` rules).
- **FR-POL-5** Policies are subject to the main bypass (INV-1).

### 4.6 System settings

When `manage_sysctls = true` (default), PolyWAN MUST set at startup, re-apply when an uplink interface is (re)created, and record the previous values in the state directory the following settings; the per-interface settings are prerequisites of path readiness and failures are handled as in FR-DISC-7. A setting that belongs to a family is changed only while that family is managed (§4.3); an IPv4-only installation changes no IPv6 setting.

- **FR-SYS-1** IPv4 forwarding (`net.ipv4.ip_forward = 1`) and, if any IPv6 path is configured, IPv6 forwarding (`net.ipv6.conf.all.forwarding = 1`).
- **FR-SYS-2** On each uplink interface: `rp_filter = 2` (loose) and `src_valid_mark = 1`, so that the reverse-path check of inbound packets uses the path mark set before routing (§4.7); without `src_valid_mark`, inbound port forwarding fails the check whenever no source rule covers the post-DNAT destination. Probe replies are not marked; their IPv4 reverse-path check succeeds through the `from` rule of the probe's source address, and the documentation MUST state this dependency (it is observable only with an empty active set and targets not covered by main routes, because loose mode accepts any route). On each uplink interface, for each managed family: `ignore_routes_with_linkdown = 1`, so that the kernel stops selecting a multipath member as soon as its interface loses carrier, before PolyWAN withdraws it (without it, connections hashed to that member fail until the withdrawal). PolyWAN MUST NOT change `net.ipv4.conf.all.rp_filter`. IPv6 has no `rp_filter`; administrators using an nftables `fib`-based reverse-path filter MUST include the mark in the lookup and run it after PolyWAN's prerouting chain (documented recipe).
- **FR-SYS-3** PolyWAN MUST NOT change `accept_ra`. Router Advertisement processing belongs to whoever manages the interface (the kernel with `accept_ra = 2`, systemd-networkd with `IPv6AcceptRA=yes`, NetworkManager). Because IPv6 forwarding (FR-SYS-1) disables the kernel's RA processing on interfaces with `accept_ra = 1`, startup and `check-config` MUST warn for each IPv6 path with `gateway = "auto"` whose uplink has `accept_ra = 1` while forwarding is or will be enabled, explaining that `accept_ra = 2` or a user-space RA client is required (`accept_ra = 0` is normal with systemd-networkd and NetworkManager). If an IPv6 path with `gateway = "auto"` has no discovered gateway 30 s after startup or after its link came up, PolyWAN MUST emit a warning that names the likely causes for each of these cases.
- **FR-SYS-4** The multipath hash policies of FR-ROUTE-5.

When `manage_sysctls = false`, PolyWAN MUST check these values at startup and warn for each one that differs, without changing it. On `cleanup`, a sysctl is restored to its recorded previous value only if its current value is still the one PolyWAN set.

### 4.7 Mark lifecycle (nftables)

This section defines what the generated ruleset (§7) does to each packet. "Restore" means copying a path value from the conntrack PolyWAN field to the packet PolyWAN field; "assign" means writing a path value into the conntrack PolyWAN field and the packet PolyWAN field.

1. **Prerouting** (filter chain, hook prerouting, priority −150: after conntrack, before DNAT):
   1. If the conntrack PolyWAN field holds a path value: restore it into the packet, for every packet of the connection, whatever its conntrack state (covers retransmitted SYNs, one-way UDP, RELATED ICMP errors). Stop.
   2. Else, if the packet arrived on uplink `id` in the original direction of its connection: assign path `id` (new inbound connection, INV-5). Stop. Reply packets of connections without a path value, such as probe replies, are left unmarked; their reverse-path check succeeds through the source rule of the probe's local address (FR-SYS-2).
   3. Else, if the packet arrived on a downlink in the original direction of its connection: evaluate policies (FR-POL-1) and, on the first match, write the policy value into the packet PolyWAN field only. Stop. Replies of connections without a path value are not policy-marked; they follow FR-ROUTE-3.
2. **Output** (route chain, hook output, priority −150, so that a mark change triggers a new routing decision):
   1. If the packet PolyWAN field holds a probe value: stop (INV-6).
   2. If the conntrack PolyWAN field holds a path value: restore it (replies of the router to inbound connections, later packets of router-originated connections).
3. **Postrouting** (filter chain, hook postrouting, priority −150: before source NAT):
   1. If the packet PolyWAN field holds a probe value: stop.
   2. If the conntrack PolyWAN field holds no path value and the packet leaves through uplink `id` in the original direction of its connection: assign path `id`. This is the only place where outgoing connections, including policy-matched ones, get their path. Replies of connections without a path value (for example connections that arrived on an interface PolyWAN does not manage) are not assigned.
4. **NAT** (nat chain, hook postrouting, priority `firewall.nat_priority`, default 100, always strictly greater than −150): §6.

All mark reads and writes use encoded values (FR-MARK-3). Marking applies only to tracked unicast traffic (§4.8): every chain first returns for untracked packets (`ct state untracked`), and the prerouting and postrouting chains also return for non-unicast packets, identified both by packet type and by destination, because tunnel uplinks deliver multicast and broadcast with packet type `host` and locally generated packets have packet type `host` in postrouting. Prerouting returns for `meta pkttype != host` and, before the inbound assignment, for IPv4 multicast and limited broadcast, IPv4 broadcast addresses (`fib daddr type broadcast`) and IPv6 multicast destinations; postrouting returns for the same destination prefixes and for broadcast addresses of the egress interface (`fib daddr . oif type broadcast`). These skips keep conntrack entries of non-unicast flows unassigned and have no routing effect. An unassigned connection is not assigned merely because its reply leaves through an uplink. Unassigned replies follow FR-ROUTE-3. Spike S2 verified this lifecycle on 6.1/nftables 1.0.6 and 7.1/nftables 1.1.3, including that every mark write compiles to constant-only bitwise operations, the original-direction condition of step 3.2 (AS-50) and the non-unicast skips.

- **FR-MARK-5** The ruleset MUST implement exactly this lifecycle. Values outside the PolyWAN field MUST be preserved (FR-MARK-1, FR-MARK-3).

### 4.8 Conntrack and offload requirements

- **FR-CT-1** Unicast data traffic between downlinks and uplinks, and unicast data traffic of the router through uplinks, MUST be tracked by conntrack for pinning to work. Untracked traffic is not marked. `notrack` rules for data traffic break pinning; `check-config` MUST warn if the administrator's ruleset contains `notrack` statements (best effort, by inspecting `nft -j list ruleset`).
- **FR-CT-2** Hardware and software nftables flow offload MUST NOT be enabled for traffic between PolyWAN downlinks and uplinks. Administrators MUST maintain this condition throughout active operation. Offloaded packets bypass the mark lifecycle of §4.7 and use cached forwarding state; retention of the conntrack path value alone does not establish compliance with the routing and rejection guarantees of §4.1.

  As a conservative compatibility check, online `check-config`, startup and reload validation MUST reject any flowtable whose device selectors match a configured uplink or downlink, whether or not `flags offload` is present. Reload validation MUST use the proposed configuration. The check MUST accept both string and array forms of JSON `dev`, compare configured interface names even when the interfaces do not exist, and conservatively treat a trailing `*` as a possible prefix selector. Diagnostics MUST identify the flowtable, matching selector and configured interface.

  The prohibition also applies when offload attaches below a configured logical interface. The documentation MUST state that direct interface-name checks alone do not establish compatibility for stacked or bridged interfaces. These checks apply in both firewall modes; PolyWAN MUST NOT modify foreign flowtables.

  During active operation, PolyWAN MUST inspect the system's flowtables at every full reconciliation (FR-REC-6) and every reload, in both firewall modes. Runtime compatibility MUST be evaluated against the running configuration; reload acceptance MUST additionally be evaluated against the proposed configuration.

  If a flowtable matches the running configuration under this requirement, PolyWAN MUST log an error identifying the flowtable, selector and interface, and add `flow_offload` to its degradation reasons. PolyWAN MUST continue normal routing management and MUST NOT stop, withdraw routes or modify foreign flowtables solely because of this finding.

  PolyWAN MUST clear `flow_offload` only after a successful full inspection during full reconciliation finds no matching flowtable. Failed or incomplete inspection MUST be reported and MUST NOT clear the reason. Other degradation reasons MUST remain independent (FR-API-2). PolyWAN MUST emit `status_degraded` and `status_recovered` on overall status transitions (FR-EV-1); clearing `flow_offload` MUST NOT emit `status_recovered` while another degradation reason remains.

  A match against only the proposed configuration MUST reject the reload without adding `flow_offload` to the running configuration's degradation reasons (FR-CFG-3).

  Runtime detection is diagnostic, not enforcement: while the administrator violates the offload prohibition, PolyWAN does not guarantee §4.1 for affected offloaded traffic, including before detection. Spike S2 (F13, `t10`) observed software flowtables with the tested TCP flows keeping their uplink but leaving without PolyWAN's packet mark, and a flowtable that lists only downlinks offloading one direction of uplink traffic; these results do not establish the guarantees of §4.1 for offloaded traffic.
- **FR-CT-3** The documentation MUST describe, without promising recovery: expired or flushed entries (the next packet that conntrack accepts as new is routed as a new connection, possibly through another uplink, and the connection usually breaks); entry allocation failure under table exhaustion (packets may be dropped by the kernel); invalid packets (not tracked as new; not marked).
- **FR-CT-4** Conntrack zones other than the default zone are not supported on uplink and downlink interfaces in 2.0 (documented limitation).
- **FR-CT-5** **Control-plane compatibility**: PolyWAN MUST NOT prevent the operating system from acquiring and maintaining uplink configuration, starting from no lease, no global address, no default route and an empty active set: DHCPv4 acquisition, renewal (except as stated below) and rebinding; DHCPv6 acquisition and maintenance, including prefix delegation, subject to the unicast exceptions below; Router Solicitation and Router Advertisement, duplicate address detection and neighbour discovery; PPP and PPPoE negotiation; the multicast and broadcast traffic these need; interface recreation and address expiry. Exception: a unicast DHCPv4 renewal towards an off-link server (provider relay) whose route lookup is not bound to the leased address (observed with ISC dhclient and dhcpcd) is unbound router-originated traffic: it is rejected while the active set is empty and balanced otherwise; the client then depends on the broadcast rebind at T2, which succeeds if the provider answers rebinds (with very short leases, some clients may let the lease expire before rebinding; observed with ISC dhclient and 2-minute leases, also without PolyWAN). Exception: DHCPv6 messages sent to a unicast address announced by the Server Unicast option follow ordinary routing; PolyWAN does not guarantee their delivery independently of the active set. This capability was obsoleted by RFC 9915. Where neither the local table nor the main bypass supplies a route, messages whose route lookup specifies neither a source address nor an interface are rejected when the active set is empty and balanced otherwise. This was observed for Request and Renew with dhcpcd 10.1.0 and 10.3.0 in manager mode. If a Request selects another uplink through which the server is unreachable, acquisition of an address or delegated prefix can remain unsuccessful. With unchanged routing and hash inputs, retransmissions can continue selecting that uplink. Acquisition has no T2 Rebind recovery; an empty active set can also prevent it until a suitable active path becomes available. ISC dhclient 4.4.3-P1 was observed to send Request by multicast and Renew by unicast with an interface constraint and a link-local source. For the tested off-link destination, that Renew uses its interface's balancing nexthop while present and is rejected otherwise; it never leaves through another interface. Interface binding alone therefore does not guarantee unicast delivery outside the active set. After unsuccessful renewal, the tested clients attempt multicast Rebind at T2. Lease and prefix maintenance then depend on a successful server response before expiry. PolyWAN MUST NOT prevent the multicast exchanges. The documentation MUST warn that these exceptions can prevent initial acquisition as well as renewal. It MUST describe the supported remedies: omit the Server Unicast option at the server, or use a client or mode that ignores it, as observed with NetworkManager 1.52.1's internal client and dhcpcd outside manager mode. ISC dhclient's multicast Request avoids the observed acquisition problem, but its unicast Renew retains the limitation above. Spike S4 established that, apart from the DHCPv4 exception, and without exercising the DHCPv6 Server Unicast cases, the listed functions work with the complete guard layout and an empty active set in the tested combinations (Linux 6.1, 6.12 and 7.1; systemd-networkd 252 and 257, NetworkManager 1.52, ISC dhclient, dhcpcd 9 and 10, the kernel's RA/SLAAC/DAD/ND, Kea DHCPv6 with prefix delegation, pppd with rp-pppoe for IPv4): DHCPv4 discovery, requests and rebinding use packet sockets, on-link renewals and link-local traffic are covered by the main bypass, IPv6 multicast is routed by the local table, PPP control traffic is not IP-routed. No exception to the guard rules is needed for these mechanisms (Q15). M2 validated IPv6 over PPPoE through AS-35 and DHCPv6 address and prefix acquisition, renewal and rebinding with the Server Unicast option through AS-44, using dhcpcd and ISC dhclient. NetworkManager 1.52.1's internal client with prefix delegation was validated in the recorded H4 virtual-machine run and ignored the option. systemd-networkd's handling of this option was not tested. DHCPv4 clients that bind the renewal to the leased address (systemd-networkd, NetworkManager) use the address's source rule and path route, available within 1 s of the address and gateway events (FR-DISC-5).

### 4.9 Coexistence with network managers

- **FR-COEX-1** At startup and in `check-config`, PolyWAN MUST read the effective systemd-networkd configuration (`networkd.conf` and drop-ins in `/etc`, `/run`, `/usr/local/lib`, `/usr/lib`, a drop-in in an earlier directory hiding one with the same name in a later directory) when systemd-networkd is active in PolyWAN's network namespace, and refuse to start if `ManageForeignRoutingPolicyRules` or `ManageForeignRoutes` is enabled (explicitly or by default), with a message explaining the fix. Rationale (S4): with them enabled, networkd deletes PolyWAN's rules on every link reconfiguration (252 and 257) and on restart (257), and PolyWAN's routes on restart. `ManageForeignNextHops` (systemd 256 and later) needs no check, because PolyWAN owns no nexthop objects and discovers routes that use single nexthop objects (FR-DISC-3). The documentation MUST include a compatibility matrix by systemd version.
- **FR-COEX-2** The documentation MUST include NetworkManager guidance (NetworkManager removes routes only in tables it manages; PolyWAN's tables MUST NOT be used as NetworkManager `route-table` values).
- **FR-COEX-3** When no ownership conflict is active (FR-COEX-4), PolyWAN MUST start restoring any of its artifacts removed or altered by a third party within 1 s of the netlink notification and, when the kernel operations succeed, complete the restoration within that second, logging an `artifact_repaired` event; when they fail, FR-REC-5 applies. Removals that the kernel performs itself as a consequence of an observed event are expected, are not counted as third-party removals (FR-COEX-4), and are handled by the normal planning path: routes of an interface that goes down or whose IPv6 configuration is reset, routes whose preferred source address is deleted, routes that use a deleted nexthop. Removals are attributed by the port id in the notification's message header (`nlmsghdr.nlmsg_pid`, not the netlink sender address, which is always the kernel: 0 means the kernel, PolyWAN's own mutation socket means PolyWAN, any other value a third party), correlated with the link and address events that explain kernel removals; removals that the kernel performs without any notification (S3: IPv4 routes on administrative down or on removal of their source address) are found by the re-reads of §12.2 and are kernel-initiated. An absence found only by a dump counts as a third-party removal only when it is confirmed (§12.2) and not explained by an observed kernel event; a single dump's absence is never counted, because dumps can omit entries (S3).
- **FR-COEX-4** If artifacts of the same kind are removed by a third party more than 3 times in 5 min, PolyWAN MUST stop immediate repairs for that kind, set its status to `degraded` with reason `ownership_conflict`, emit an event, and repair only at each full reconciliation (FR-REC-6). The conflict is cleared, with an event, after two consecutive full reconciliations that find no third-party removal.

## 5. Uplink discovery and health

### 5.1 Discovery

- **FR-DISC-1** Interface identity is the configured interface name; PolyWAN tracks its ifindex. When the interface disappears, its paths become not ready; when an interface with the same name appears (for example a PPP interface recreated with a new ifindex), discovery starts again and per-interface sysctls are re-applied.
- **FR-DISC-2** Two address sets are derived for each path:
  - **Local addresses**: the interface's addresses of the family with global scope that are not tentative or DAD-failed (temporary and deprecated addresses included, because they remain valid for existing and service traffic; for IPv4, primary and secondary addresses), plus a static `source` assigned to another interface (FR-DISC-6). Every local address gets a `from` rule and a source guard (FR-ROUTE-3).
  - **Source candidates**: the local addresses on the interface itself that are neither temporary nor deprecated. The **source** of the path, `source = "auto"` (default), is the candidate chosen by preferring permanent addresses over dynamic ones, then primary over secondary (IPv4), then the numerically lowest. With a static `source`, the path is ready only while that address is present on the router and not tentative, DAD-failed or deprecated.

  An address that belongs to the local addresses of two paths of the same family makes both paths not ready, with reason `address_conflict`; configuration validation MUST reject the same static `source` on two uplinks.
- **FR-DISC-3** Next hop, `gateway = "auto"` (default):
  - IPv4 point-to-point interfaces (`IFF_POINTOPOINT`): no gateway is needed and routes use `dev <iface>`.
  - Otherwise (including every IPv6 path, because the kernel rejects device-only members in IPv6 multipath routes): PolyWAN considers default routes of the family, of type unicast, in the tables listed in `discovery_tables` (default `["main"]`), not installed by PolyWAN, with an inline nexthop or inline multipath members that use the uplink interface, excluding members flagged `dead` or `linkdown`. It selects by lowest metric, then (IPv6) highest router preference, then order of `discovery_tables`, then numerically lowest gateway. Flags relevant to reachability (`onlink`) are preserved from the source route. Routes whose observed expiry has passed MUST NOT be selected, subject to the expiry re-read of FR-DISC-5.
  - A route that references a nexthop object (`RTA_NH_ID`) is recognised by that attribute, although the kernel also dumps the resolved gateway and interface. A single (non-group) nexthop object with a gateway on the uplink interface is resolved and used like an inline nexthop; systemd-networkd installs Router Advertisement default routes this way by default (observed with 257; the option appeared in 256). The Observer (§12.2) also subscribes to nexthop notifications and dumps nexthop objects; when a nexthop object used by a discovered route changes or is deleted, the paths that depend on it are re-evaluated within the bound of FR-DISC-5. Resolution and nexthop notifications were not exercised by the spikes; M2 validated them (AS-49). Routes that reference nexthop groups are not used; if they are the only candidates, the path is not ready and a warning recommends a static `gateway`.
  - The kernel changes the `dead` and `linkdown` flags of nexthops without notification; readiness is re-evaluated from the re-reads of §12.2 after link events.
  - Absence from one dump alone MUST NOT remove a discovered route from the observed view; absence requires confirmation (§12.2). This does not make an expired route eligible for discovery (FR-DISC-5). The confirming read takes milliseconds, within the bound of FR-DISC-5 (S3: the higher-metric IPv6 default routes of main disappeared from some dumps while main changed).
  - The next hop is represented as (gateway address, ifindex); identical gateways on different uplinks (for example `fe80::1`) are therefore distinct.
  - An IPv6 path on a point-to-point interface (for example PPP) is ready only when a gateway is discovered (typically the peer's link-local address from its Router Advertisement) or configured.
- **FR-DISC-4** A static `gateway` is used as configured; the path is ready while the interface is up with carrier, has a usable source address, and the gateway is reachable on the interface: covered by a connected route of the interface in the main table, or declared with `gateway_onlink = true`.
- **FR-DISC-5** Discovery MUST be event-driven (§12.2). Any change of carrier, ifindex, address or gateway MUST be reported as an event (§8) and the first attempt to update PolyWAN's artifacts MUST start within 1 s; when the kernel operations succeed, the update completes within 1 s, otherwise FR-REC-5 applies. Discovery MUST account for default-route lifetime refresh, shortening and expiry within the bounds above, without depending on a route notification. These notifications are not reliably supplied by the kernel for Router Advertisement routes. PolyWAN MUST track observed expiry deadlines and re-read the affected discovery tables when those deadlines pass, before evaluating the affected paths, because an unnotified refresh may have extended a deadline. A route whose refreshed observation remains expired MUST be excluded from discovery even if the kernel still lists it. The Observer MUST also receive Router Advertisements on a raw ICMPv6 socket, including advertisements without prefix information, and schedule re-reads of the discovery tables containing observed IPv6 advertised or expiring default routes through the receiving uplink. Reports MUST be coalesced by receiving interface over a bounded window that preserves the discovery deadline; the implementation uses 100 ms windows.
- **FR-DISC-6** IPv6 uplinks that have no global address of their own (prefix-delegation-only providers) are supported only with a static `source` assigned to another interface of the router (typically the LAN address taken from the delegated prefix) and `nat = "snat"`. Automatic handling is out of scope for 2.0.
- **FR-DISC-7** A path whose routes cannot be installed (the kernel rejects them) is not ready, with reason `route_install_failed`, the operation, errno and netlink extended acknowledgement in the event; installation is retried at each discovery change and full reconciliation.

  With `manage_sysctls = true`, the applicable per-interface settings of FR-SYS-2 are prerequisites for path readiness. While their application is pending or has failed, otherwise-ready paths on that interface are not ready with reason `route_install_failed`; existing discovery-failure reasons retain precedence. A failure also emits `apply_failed`, identifying the interface, the failing setting or prerequisite operation, and the error, and keeps the status `degraded` until the desired generation is fully applied (FR-REC-5). Sysctl errors report errno where available; netlink extended acknowledgement is not applicable.

  Interfaces are retried independently with exponential backoff from 1 s to 60 s. A failed interface does not block reconciliation for other interfaces. Recreation of an interface invalidates the previous incarnation's backoff, with the first attempt subject to FR-DISC-5. Work for interfaces no longer configured is cancelled; unchanged work may retain its backoff across an unrelated reload.

  A failure applying a global setting (FR-SYS-1, FR-SYS-4) does not itself change path readiness. Readiness and health evaluation continue, but the reconciliation pass performs no route or rule mutations until global application succeeds; failure reporting and retry follow FR-REC-5. These rules apply from startup on. With `manage_sysctls = false`, differing values (or values that cannot be read) produce warnings as specified in §4.6 and impose no readiness prerequisite.
- **FR-DISC-8** `check-config` and startup MUST warn when a downlink's connected prefixes are missing from the main table (for example because the address was configured with `noprefixroute` or into another table): replies towards that network would otherwise follow a path table to the provider.
- **FR-DISC-9** The `type = static | ppp` setting of 1.x disappears. 1.x issue #19 (DHCP uplinks) is solved by FR-DISC-3.

### 5.2 Probes

- **FR-PROBE-1** Each probe socket MUST be created non-blocking, bound to the path's source address, with `SO_BINDTODEVICE` set to the uplink interface and `SO_MARK` set to the encoded probe value of the uplink, all before the first packet is sent. Together with the probe rules (FR-ROUTE-3) and the path table, this implements INV-6. ICMP probes use raw sockets (`SOCK_RAW`), because ping sockets depend on `net.ipv4.ping_group_range`, which PolyWAN must not change. A probe socket is tied to one interface index and one source address and is recreated when either changes. Probing of a path stops as soon as the path is not ready: guard rules do not stop device-bound IPv4 probes (§4.1.1). Probes MUST NOT depend on external binaries.
- **FR-PROBE-2** Probe types: `icmp` (ICMP echo / ICMPv6 echo, default) and `tcp` (TCP handshake to a given port, for links that filter ICMP; a SYN-ACK or a RST counts as a reply, a timeout as a loss). Targets are written as `icmp:ADDRESS`, `tcp:IPV4:PORT` or `tcp:[IPV6]:PORT`, are configured per family, and MUST be global unicast addresses that are neither local to the router nor inside a downlink prefix. Global unicast is part of configuration validation. Locality depends on the system: online `check-config`, startup and reload validation MUST reject a target equal to an address of the router, on any interface, or inside the connected network of an address of a downlink, comparing with the addresses present at validation; addresses that appear later are not re-evaluated. A startup refused for this reason exits with status 1, like the other system checks (§9); a reload is rejected with `reload_failed`, retaining the running configuration (FR-CFG-3).
- **FR-PROBE-3** Replies MUST be validated: source address equal to the target; for ICMP, matching identifier (random per path), sequence number (incremented per attempt, wrapping allowed) and a random 16-byte payload token unique per attempt; for TCP, a SYN-ACK or a RST on the attempt's own socket; arrival before the attempt deadline. For IPv4 ICMP the checksum is verified in user space (raw sockets receive messages before the kernel validates it). ICMP errors and local errors (such as `ENETUNREACH`) count as losses, not replies, for both probe types; a reply is matched only to an attempt that is still open. Results of attempts started under a previous interface, address or configuration generation MUST be discarded and counted as **cancelled**, not as losses.
- **FR-PROBE-4** Scheduling: rounds start every `interval` (default 5 s) at a fixed rate, per path, and never overlap. In a round, all targets are probed concurrently; each target gets up to `attempts` attempts (default 2), each waiting up to `timeout` (default 1 s), the next attempt being sent only after the previous one timed out. A target is **reachable** if any attempt got a valid reply. The round **passes** if at least `required_reachable` targets (default 2) are reachable. Without quality gates, a round ends as soon as its outcome is certain; with quality gates enabled for the path, every started attempt runs until it gets a reply or reaches its deadline, so that samples are not biased. A round lasts at most `timeout × attempts`. A TCP attempt is one socket; when `timeout` reaches the kernel's initial SYN retransmission timeout (1 s) it may carry a retransmitted SYN, and it still yields at most one sample. Validation MUST require `timeout × attempts < interval` and `required_reachable ≤ number of distinct targets`.
- **FR-PROBE-5** Each completed attempt is a **sample** (replied or lost, RTT if replied); cancelled attempts are not samples. Optional quality gates per path, evaluated at the end of each round over the samples of the last `quality_window` rounds (default 6): loss ratio = lost samples / samples; RTT = median RTT of replied samples; jitter = median of absolute differences between consecutive RTTs of the same target. The loss gate is evaluated only with at least `quality_min_samples` samples (default 10); the RTT and jitter gates only with at least 5 replied samples or 5 RTT differences respectively. Validation MUST require `quality_min_samples ≤ targets × quality_window`. A round that passes reachability but violates a gate counts as **failed (degraded)**. Because old samples stay in the window, recovery from a degraded state takes at least `rise` rounds and until the window no longer violates the gate; the documentation MUST say so.
  Window statistics are computed and published whether or not quality gates are enabled. Without gates, early termination under FR-PROBE-4 means these statistics describe completed attempts only and may favour faster targets; cancelled attempts are excluded, never counted as losses. The documentation MUST explain this limitation.
  The window is cleared when the probing generation changes or the path stops being ready, but not merely when health changes to `down`. A reload preserving probing and sampling behaviour retains the window. A reduced `quality_window` discards excess oldest rounds; an increased window accumulates additional rounds prospectively. Revised thresholds and minimum sample counts apply at the next completed round. A statistic without the inputs needed to compute it is unavailable, not zero.
- **FR-PROBE-6** Default targets MUST be well-known anycast resolvers of at least three different operators for each family, and the documentation MUST explain why nearby hosts (such as the provider's own router) are bad targets (as in the 1.x README).

### 5.3 Health state machine

Each path is in one of two states: `down` or `up`. Health is independent of selection: a path can be `down` and still active when `all_down_policy` keeps it (§4.4).

- **FR-HEALTH-1** **Initial state**: readiness is applied first: a path that is not ready starts `down`. For a ready path:
  - Warm start (a valid health checkpoint from the same boot, §12.3, taken less than 10 min earlier by `CLOCK_BOOTTIME`): the path starts in its checkpointed state with its hysteresis counters, and normal hysteresis applies.
  - Cold start (otherwise, including after a reboot): the path starts `up`; the first completed round sets the state directly, without hysteresis.

  This prevents a restart from briefly re-activating a path that was down.
- **FR-HEALTH-2** `up` → `down` after `fall` consecutive failed rounds (default 2). `down` → `up` after `rise` consecutive passed rounds (default 3).
- **FR-HEALTH-3** A path that stops being ready goes `down` immediately, without waiting for `fall`; when it becomes ready again, it needs `rise` passed rounds to go `up` (startup optimism applies only to cold start).
- **FR-HEALTH-4** Every transition records a reason (`probe_failed`, `degraded`, `carrier_lost`, `interface_removed`, `address_lost`, `address_conflict`, `gateway_lost`, `route_install_failed`, `probes_recovered`, `startup`) shown in events, the API and logs.
- **FR-HEALTH-5** Detection bounds with default settings, which acceptance tests MUST verify: loss of carrier or interface → path `down` and its routes withdrawn within 1 s; silent upstream failure → path `down` within `(fall + 1) × interval + timeout × attempts` (17 s with defaults). Removal from the active set follows from the state change according to §4.4 (a `down` path stays active only under `all_down_policy` with no healthy candidate).

## 6. NAT

- **FR-NAT-1** Per path, `nat` can be:
  - `masquerade`: source NAT to the address of the outgoing interface; works with dynamic addresses;
  - `snat`: source NAT to the static address given in `source` (MUST be static);
  - `none`: no NAT (routed setups).

  For IPv4 the default is `masquerade`. For IPv6 there is no default: `nat` MUST be set explicitly whenever IPv6 is enabled on an uplink, and the documentation MUST explain the trade-offs (with several providers, `none` only works if every provider routes the LAN prefix, which is rare; masquerade with a ULA LAN prefix gives transparent failover at the cost of end-to-end addressing).
- **FR-NAT-2** NAT applies only to traffic coming from downlinks and leaving through the uplink. Traffic forwarded between downlinks and router-originated traffic are never translated.
- **FR-NAT-3** Port forwarding (DNAT) remains the administrator's responsibility; INV-5 guarantees symmetric replies.
- **FR-NAT-4** If the administrator also performs source NAT on uplink interfaces, the earliest NAT chain to match decides. The documentation MUST say that `nat = "none"` must then be set, and `check-config` MUST warn when it finds `masquerade` or `snat` statements on uplink interfaces in other tables (best effort).

## 7. Firewall integration

### 7.1 Modes

- **FR-FW-1** `firewall.mode = "managed"` (default): PolyWAN creates and owns the nftables table `inet polywan` and replaces it atomically (one transaction containing `add table`, `delete table`, and the full table) at startup, on reload and when reconciliation finds it missing or different (§12.2). It MUST NOT modify any other table.
- **FR-FW-2** `firewall.mode = "external"`: PolyWAN performs no nftables mutations (read-only inspection, such as the checks of FR-CT-1, FR-CT-2 and FR-NAT-4, still happens). The administrator loads the ruleset produced by `polywan export-nft`. The daemon MUST log at startup that marking and NAT are the administrator's responsibility, and MUST check that a table with the expected name exists, warning if it does not.
- **FR-FW-3** Both modes MUST use the same generator, so that `export-nft` prints exactly what the managed mode installs. The text follows the layout of `nft list ruleset` (`table_print` in nftables): tab indentation and a blank line between chains; it is not byte-identical to it, since `nft` normalises what it lists (priority names, folded constants). Each chain carries a `comment` attribute stating its purpose, and each uplink or policy rule one identifying the uplink by name and id, the family and, for a policy, its name, so that the explanations remain visible in the loaded ruleset. A comment holds at most 128 bytes (the nftables limit), truncated on a UTF-8 character boundary; double quotes and control characters from configuration text are replaced, since an nftables quoted string cannot contain them. Longer explanations MAY appear as `#` lines, which nftables does not retain.

### 7.2 Ruleset properties

- **FR-FW-4** The ruleset contains only the chains of §4.7 with the stated hook types and priorities, plus the NAT chain. It MUST NOT contain `drop`, `reject` or `accept` verdicts (INV-7); chains have policy `accept` and only use `return` to stop processing.
- **FR-FW-5** The ruleset MUST be generated from the configuration only, never from runtime state (health, addresses, active set). All runtime changes happen in routing (FR-ROUTE-3). Re-installing identical content during reconciliation is allowed.
- **FR-FW-6** The documentation MUST explain interactions with the administrator's ruleset: chains of other tables at the same hooks run independently in priority order; a `drop` anywhere drops; another writer of the same mark bits later in the pipeline breaks pinning; DNAT in prerouting at priority −100 runs after PolyWAN's marking; rules of other tables that read or write conntrack marks must use priorities above −200, because at −200 they can run before the conntrack entry exists (S2). The documentation MUST explain that flowtable hits bypass PolyWAN's prerouting and postrouting marking chains and the classic forwarding path. PolyWAN therefore does not restore their packet-mark field; S2 observed an empty field despite a retained conntrack path value. Packet-mark consumers and counters in bypassed chains cannot assume the normal lifecycle. The software-flowtable results of S2 F13 MUST NOT be presented as a general guarantee of offload compatibility. FR-CT-2 applies even when only downlinks are listed.

## 8. Events and notifications

### 8.1 Events

- **FR-EV-1** Event types: `daemon_started`, `daemon_stopping`, `config_reloaded`, `reload_failed`, `path_state_changed`, `path_address_changed`, `path_gateway_changed`, `active_set_changed`, `uplink_drained`, `uplink_undrained`, `artifact_repaired`, `apply_failed`, `status_degraded`, `status_recovered`.
- **FR-EV-2** Every event has: sequence number (monotonic within a daemon run), instance identifier (random per daemon run), timestamp, type, uplink and family where applicable, old and new values, reason, and a human-readable message.
- **FR-EV-3** Events are logged and dispatched to notifiers through bounded queues; when a queue is full, the event is dropped for that notifier and a counter is incremented (INV-8).

### 8.2 Email

- **FR-MAIL-1** When `[notify.email]` is configured, PolyWAN submits email by executing the absolute path `notify.email.sendmail` (default `/usr/sbin/sendmail`) with the argument vector `["-i", "-f", FROM, RECIPIENT...]`, without shell interpretation and without `-t`. The complete message is written to standard input, which is then closed. Successful submission requires successful completion of the input write and exit status 0. Spawn errors, input errors, termination by signal, non-zero exit status and expiry of the 60 s submission deadline (covering the input write and the wait for the command) are failures under FR-MAIL-3. Success means acceptance by the mail system, not delivery to the recipient.
  The command runs with UID 0, primary GID 0 and no supplementary groups, within the daemon's service sandbox. Its environment contains only `PATH=/usr/sbin:/usr/bin:/sbin:/bin`; its working directory is `/`; it inherits no descriptors other than standard input, output and error; it runs in a new process group. On timeout or cancellation PolyWAN MUST kill that process group and reap the direct child. Standard output is discarded. Standard error is drained asynchronously, with at most 64 KiB retained and an explicit truncation indication; reaching that limit MUST NOT stop draining or block the child. Diagnostics are escaped before logging and MUST NOT enter status or event responses. The hook user and the hooks' removal of capabilities (FR-HOOK-3) do not apply to sendmail: running it as root is a trust decision, and neither path ownership (FR-CFG-5) nor process-group killing contains a malicious trusted program or descendants that leave the group.
  `from` and each entry of the non-empty `to` list MUST be a single ASCII mailbox of the form `local-part@domain`: an unquoted dot-atom local part and a DNS domain. Display names, several addresses in one entry, comments, whitespace, control characters, a leading `-`, and file or program recipient syntax are rejected. PolyWAN constructs an RFC 5322 message with `Date`, `Message-ID`, `From`, `To`, a fixed ASCII `Subject`, `MIME-Version: 1.0` and a MIME `text/plain; charset=UTF-8` body encoded as base64 or quoted-printable, with header folding and line lengths conforming to the message and MIME specifications. Event text, interface descriptions and diagnostics MUST NOT be interpolated into headers. The Subject is `PolyWAN notification`, `PolyWAN notifications suppressed`, or `PolyWAN notification test`, according to message kind. Append ` (HOST)` only when the kernel hostname is non-empty, at most 63 ASCII octets in total, and consists of dot-separated non-empty labels containing only letters, digits and hyphens, with no leading or trailing hyphen. Otherwise omit the suffix. No DNS lookup is performed. Message and queue limits are specified in FR-MAIL-2.
  On an accepted reload, a running submission or an admitted notification test finishes with the configuration it started with. Pending ordinary notifications and retries use the newly accepted email configuration; their messages are rebuilt as necessary, keeping their Message-ID. Removing `[notify.email]` discards pending email and retries, logging their number. A reload resets neither rate-limit accounting nor retry counts. Every execution uses a path that satisfies FR-CFG-5 at that time.
  PolyWAN implements no SMTP, TLS, authentication or mail-system configuration: the trusted executable, its configuration and helpers, sender rewriting, relay policy and later delivery are the administrator's.
- **FR-MAIL-2** `notify.email.events` selects ordinary event types for email. Its default is `daemon_started`, `daemon_stopping`, `config_reloaded`, `reload_failed`, `path_state_changed`, `active_set_changed`, `uplink_drained`, `uplink_undrained`, `status_degraded`, `status_recovered`. An explicit list replaces the default, MUST be non-empty and MUST contain only FR-EV-1 types; duplicates have no additional effect. Selection occurs before admission to the email event queue. Changing the selection affects subsequently emitted events; already retained batches and messages remain subject to FR-MAIL-1. The default leaves out routine address and gateway changes and repeated repair and failure events; `status_degraded` is emitted only on the overall transition to `degraded` (FR-EV-1, FR-CT-2), so a later additional degradation reason produces no default email.
  Selected events are coalesced over `coalesce` (default 30 s) into one email listing retained changes and identifying omissions. At most `max_per_hour` distinct notification messages (default 20) are admitted in a rolling hour, plus at most one suppression notice in a rolling hour when that limit suppresses notifications. Retries retain their original admission slot. Notification tests neither consume nor reset these limits and do not flush, delay or merge with an ordinary batch.
  The email event queue is limited to 256 events and 1 MiB of serialised event data; exceeding either limit drops the incoming event and increments the FR-EV-3 counter. Each coalescing batch retains at most 200 changes and 64 KiB of rendered change text; further changes are counted for an omission line. Any additional retained representation of the batch MUST also have a documented finite byte bound.
  Message bodies are limited to 128 KiB before transfer encoding, including omission notices; complete encoded messages, including headers, are limited to 512 KiB. Truncation preserves valid UTF-8 and MIME syntax. Required headers and recipients MUST NOT be silently truncated; inability to construct a conforming message is reported as a notification failure.
  At most eight ordinary messages await initial submission or retry, with at most 4 MiB of total retained message data across their representations. Admission beyond either bound evicts the oldest waiting message and logs the loss. Eviction does not refund rate-limit admission. The running submission is separate from this queue. Suppression retains a count of suppressed messages, not their contents; storage drops and deliberate event filtering are not rate-limit suppression.
- **FR-MAIL-3** A failed submission is retried at most three times, 1, 5 and 15 min after the preceding failure, then dropped and logged. Retries keep the same logical message and Message-ID. No retry follows a successful submission; later delivery and bounces belong to the mail system. A failure or timeout can follow partial or complete acceptance, so duplicate delivery is possible and exactly-once delivery is not promised. Pending retries are bounded and follow FR-MAIL-1's reload rules. At most one sendmail submission runs at a time; tests and retries share this limit.
  At shutdown, email is flushed on a best-effort basis within 10 s: the open batch is closed (subject to the FR-MAIL-2 limits), a running ordinary submission is allowed to finish, then each waiting message whose initial submission or retry is due is submitted once, without further retries, each taking the shared sendmail turn, which can mean waiting for a notification test that holds it. Retries not yet due keep their delay and are discarded with a warning, as is whatever remains when the 10 s expire. Notification tests are not otherwise waited for: a test still running when the daemon stops is cancelled. The flush never delays the routing shutdown of IMPL-7 beyond this bound.
- **FR-MAIL-4** `polywan notify-test` calls `POST /v1/notify-test` on the control socket and tests the daemon's accepted configuration inside its execution environment. It attempts one test through every configured channel, bypassing ordinary coalescing, the email rate limit, and email and hook event filters, without changing their accounting or pending work. Hooks receive a synthetic event of type `notify_test` with `test: true`, which is not inserted into the event ring. Tests are not retried.
  At most one test runs at a time; tests share the subprocess concurrency limits and create no unbounded queued work. The response reports each channel as succeeded, failed, timed out or not started, with the exit status or signal where available and the bounded standard error with its truncation flag. An admission failure starts no channel and returns 503; an overlapping test returns 429. The test has an overall budget of 60 s plus the sum of the configured hook timeouts; at its expiry, outstanding test processes are cancelled and unstarted channels reported as such. The CLI exits non-zero if any channel fails or no channel is configured. A client disconnection triggers neither a second submission nor a retry.
  There is no automatic local fallback on a connection or permission failure. `notify-test --offline [--config PATH]` requires root, validates executable trust and holds the instance lock while it tests locally; it refuses to run while another process holds the lock and reports prominently that the service's sandbox was not exercised. 1.x called this `email_test`.

### 8.3 Hooks

- **FR-HOOK-1** Hooks are external commands configured with an absolute executable path and an argument vector (no shell interpretation), and an optional list of event types.
- **FR-HOOK-2** The event is passed as JSON on stdin and as environment variables (`POLYWAN_EVENT`, `POLYWAN_UPLINK`, `POLYWAN_FAMILY`, `POLYWAN_OLD`, `POLYWAN_NEW`, `POLYWAN_REASON`); the rest of the environment is empty except `PATH=/usr/sbin:/usr/bin:/sbin:/bin`.
- **FR-HOOK-3** Hooks run as `hook_user` (default `nobody`), which MUST be an existing user other than UID 0 (an account with UID 0 keeps capabilities): it is rejected at startup and reload, and no hook runs while the user resolves to UID 0 at run time, and this is logged. They run with its primary group, no supplementary groups, no capabilities, no inherited file descriptors other than stdin/stdout/stderr, in a new process group, with a timeout (default 10 s) after which the whole process group is killed. Concurrency is limited (default 4); stdout and stderr are captured up to 64 KiB each and logged with the exit status.
- **FR-HOOK-4** Hooks are fire-and-forget: they cannot veto or delay routing changes (INV-8).

## 9. Status API and CLI

- **FR-API-1** The daemon serves HTTP/1.1 with JSON bodies on two filesystem Unix sockets. The **control socket**, `api.socket` (default `/run/polywan/api.sock`), is owned by root and group `api.group` (default `polywan`, created by the package), mode 0660, and exposes every endpoint. Membership of that group grants full control; the documentation MUST say so.
  The **status socket**, `api.status_socket` (default `/run/polywan/status.sock`), exposes only the read endpoints of FR-API-2. It is owned by root:root with mode 0666 (on Linux, connecting to a stream socket needs write permission; read-only behaviour comes from the endpoint allowlist), unless `api.status_group` names an existing group, in which case it is owned by root and that group with mode 0660. An empty `api.status_socket` disables it. Authorisation is fixed by the listener that accepted the connection and MUST NOT depend on headers, method overrides or dispatch to the control endpoints. Unsupported paths return 404 and unsupported methods on exposed paths 405, without side effects.
  Enabled socket paths MUST be absolute, distinct and within the platform's Unix-socket path limit. Their parent directories MUST be owned by root and not writable by group or others, also through symbolic links, and traversable by the intended clients. Ownership and mode are set before any request is served, with no transiently permissive control socket. PolyWAN MUST refuse a path occupied by a foreign or unidentifiable object. Root ownership and possession of the instance lock do not establish that an existing socket belongs to PolyWAN. Replacement is allowed only for a socket created by the current instance or positively identified by protected PolyWAN ownership metadata. A stale socket without sufficient ownership evidence requires explicit administrator removal. Symbolic links and non-socket objects are refused. Replacement sockets receive their final ownership and permissions before publication by rename. On endpoint removal or shutdown, PolyWAN unlinks a socket pathname only if its filesystem device and inode still match the socket it published; a replacement object is left untouched.
  Listener and permission changes on reload are prepared before the new configuration is committed; a failure rejects the reload and keeps the running configuration and access policy. Changing an endpoint's path or access policy, or disabling it, closes its existing connections. A reload MUST NOT swap the control and status roles of an existing path.
  The documentation MUST state that the default status socket discloses current and historical operational network information (addresses, gateways, health, drain state, reasons and event messages) to every local process able to connect, and how to restrict it (`api.status_group`) or disable it.
- **FR-API-2** Both sockets expose `GET /v1/status` (version, uptime, configuration digest, desired and applied generations, overall status `ok`/`degraded` with reasons, per-path state, reason, since, addresses, gateway, last round statistics, active sets, drain flags) and `GET /v1/events?instance=ID&after=SEQ&limit=N&wait=SECONDS`. Events are kept in an in-memory ring bounded by 1000 entries and 4 MiB of serialised event data, evicting the oldest entry when either bound is reached. With `wait`, the request blocks up to 60 s until a newer event exists. The response carries the instance identifier, a `reset` flag when the requested instance differs from the current one or `after` is beyond the latest sequence number, in which case events are returned from the start of the buffer, and a `truncated` flag when requested history has been evicted. A response holds at most 1000 events and 4 MiB, fewer when necessary; clients continue after the last returned sequence number.
  These are public operational representations: they MUST NOT include configuration contents, notification addresses or arguments, credentials, raw configuration-validation excerpts, or the output of hooks or sendmail. Reasons and messages are built from explicitly selected operational fields, never by formatting arbitrary error chains. Historical addresses and operational messages remain visible by design; the configuration digest is an identifier, not a confidentiality mechanism.
- **FR-API-3** Write endpoints, on the control socket only: `POST /v1/uplinks/{name}/drain` (body `{"force": bool}`, FR-SEL-4), `POST /v1/uplinks/{name}/undrain`, `POST /v1/uplinks/{name}/forget` (FR-MARK-4; refused while the uplink is configured), `POST /v1/reload` (response reports success, validation errors, or partial application with the failed steps), `POST /v1/notify-test` (empty body, FR-MAIL-4; it accepts no command, recipient or configuration override).
- **FR-API-4** The control socket, the status socket and the metrics listener each accept at most 16 concurrent connections, enforced before connection tasks or waiters are created; a connection beyond the limit is closed at once or left in the kernel's listen backlog, never queued in the daemon. Each connection handles one request at a time. Request bodies are limited to 64 KiB as consumed, chunked bodies included; request heads and trailers to 8 KiB each and 64 header fields. Oversized input is rejected and the connection closed.
  Ordinary requests have a 10 s deadline covering the header and body reads, the handling and the response write; idle keep-alive connections are closed after 10 s. An events request may additionally wait up to 60 s for an event; a notification test may additionally use the budget of FR-MAIL-4; neither exception lifts the input or response-write deadlines.
  Request processing has bounded work and bounded response buffering, and diagnostics about clients are rate-limited. Read requests MUST NOT enqueue routing work or hold the routing state while waiting or writing. Saturation of the status socket or the metrics listener MUST NOT consume control-socket capacity or delay the routing deadlines specified elsewhere (INV-8).
- **FR-API-5** The API is versioned (`/v1`), documented, and backward compatible within a major version.

CLI (single binary `polywan`):

| Command | Purpose |
|---|---|
| `run [--config PATH] [--dry-run] [--reset-state]` | Run the daemon in the foreground; `--reset-state` discards drain state and health checkpoints; manifest handling follows IMPL-6. `--dry-run` computes and logs every artifact change without applying it and writes nothing: no kernel or nftables changes, no state files, no control or status socket or metrics listener, no hook or sendmail execution; read-only netlink observation and probes are allowed (replaces 1.x `--demo`). It computes and logs one plan, then exits: it is a one-shot command, not a service mode, and sends no systemd readiness notification. |
| `check-config [--config PATH] [--offline]` | Validate the configuration; without `--offline`, also the system prerequisites (kernel, nftables, sysctls, systemd-networkd settings, collisions, flowtables). Exit non-zero on error. |
| `generate-config` | Print the commented example configuration that the packages install (DIST-1), embedded in the binary for installations from the static binary; no host discovery. |
| `export-nft [--config PATH]` | Print the nftables ruleset (§7). |
| `status [--json] [--socket PATH]` | Show the daemon status, through the status socket by default; `--socket` selects another API socket (the control socket when the status socket is disabled). Does not read the configuration. The human output shows, for every path, its health state and reason, whether it is ready and whether it is in the active set, and for every uplink whether it is drained. Success means the status was retrieved, also while the daemon is degraded. |
| `events [--follow] [--json] [--socket PATH]` | Show recent events, through the status socket by default; `--follow` long-polls `GET /v1/events` and handles `reset` and `truncated`. `--json` prints one JSON object per line: each event as the API returns it, and a record for each `reset` or `truncated` notice. |
| `drain NAME [--force] [--socket PATH]` / `undrain NAME [--socket PATH]` | Runtime maintenance of an uplink, through the control socket. |
| `reload [--socket PATH]` | Reload the configuration through the control socket (equivalent to SIGHUP). |
| `notify-test [--socket PATH]` / `notify-test --offline [--config PATH]` | Test every configured notification channel through the daemon and report each channel's outcome; `--offline` tests locally, as root, holding the instance lock, outside the service's sandbox (FR-MAIL-4). |
| `forget-uplink NAME [--socket PATH] [--config PATH]` | Release the persisted id binding of a removed uplink (FR-MARK-4). While the daemon runs, it goes through the control socket; offline it requires root, the configuration and the instance lock. A permission or protocol failure never falls back to offline execution. |
| `cleanup [--config PATH]` | Remove every PolyWAN artifact listed in the manifest and the configuration (1.x issue #22). Takes the instance lock, so it is refused while the daemon runs. |

The API commands use `/run/polywan/status.sock` for `status` and `events` and `/run/polywan/api.sock` otherwise; `--socket` selects other paths, so clients need not read the root-owned configuration.

Commands exit with status 0 on success, 1 on failure and 2 on a usage error; machine-readable output goes to standard output and diagnostics to standard error. `run` exits with status 78 (`EX_CONFIG`) when its configuration file cannot be read, parsed or validated (FR-CFG-1); a configured path fails FR-CFG-5; a required configured account is absent or prohibited; or the configuration conflicts with the manifest's structural settings or recorded uplink identities (FR-CFG-4, FR-MARK-4). The unit does not automatically restart an exit with status 78 (IMPL-10). Other failures that terminate startup, including account lookup errors and fatal state-file errors under IMPL-6, exit with status 1. This does not change IMPL-6's health-checkpoint fallback or `--reset-state` behaviour.

## 10. Metrics

- **FR-MET-1** Optional Prometheus endpoint, disabled unless `metrics.listen` is set (for example `127.0.0.1:9750`). It MUST serve only `GET /metrics`, with the same connection limits as the API. Metrics listener changes are prepared before configuration commitment. A bind failure rejects the reload and preserves the running listener. Changing `metrics.listen` or disabling metrics closes existing metrics connections upon commitment.
- **FR-MET-2** Metrics (labels in braces): `polywan_build_info{version}`, `polywan_status_degraded`, `polywan_path_up{uplink,family}`, `polywan_path_ready{uplink,family}`, `polywan_path_active{uplink,family}`, `polywan_uplink_drained{uplink}`, `polywan_path_rtt_seconds{uplink,family}`, `polywan_path_jitter_seconds{uplink,family}`, `polywan_path_loss_ratio{uplink,family}`, `polywan_path_transitions_total{uplink,family,to}`, `polywan_probe_samples_total{uplink,family,target,result}`, `polywan_artifact_repairs_total{kind}`, `polywan_apply_failures_total{kind}`, `polywan_events_dropped_total{notifier}`, `polywan_notifications_failed_total{channel}`. `polywan_notifications_failed_total` counts failed attempts, each retry included, and excludes notification tests, whose outcome is reported to the caller (FR-MAIL-4).

## 11. Configuration

### 11.1 Format and lifecycle

- **FR-CFG-1** TOML, default path `/etc/polywan/config.toml`. Unknown keys MUST be rejected with a precise message (file, line, key). The file carries no version key: 1.x configurations are YAML (FR-CFG-6), so there is no earlier schema to distinguish. Should a later release need an incompatible schema, it would add an optional `schema_version` key whose absence means this schema.
- **FR-CFG-2** Durations use human-readable strings (`"5s"`, `"500ms"`).
- **FR-CFG-3** On SIGHUP or `reload`, the new configuration is fully validated first; if invalid, the running configuration is kept and a `reload_failed` event is emitted. If valid, it is applied by reconciliation (§12.2), without restarting probes of unchanged paths and without affecting connections of unchanged uplinks.
- **FR-CFG-4** Structural settings (`fwmark_mask`, `table_base`, `rule_priority_base`, `route_protocol`, `firewall.mode`) cannot change on reload; the documentation describes the disruptive procedure (`cleanup`, then restart). `state_dir` MUST NOT change on reload; such a reload is rejected with `reload_failed`, retaining the running configuration (FR-CFG-3). It is not a structural setting and is not recorded in the manifest. To relocate it, stop the daemon with `on_shutdown = "keep"`, move the complete state directory while preserving its ownership, permissions and contents (IMPL-5), update the configuration and any service sandbox paths (IMPL-10), then restart. No cleanup is required. Connection continuity is subject to the warm-adoption conditions of FR-REC-8; relocation does not provide an unconditional no-outage guarantee.
- **FR-CFG-5** The configuration file and its parent directories MUST be owned by root and not writable by group or others; otherwise the daemon refuses to start. The same requirements apply to `firewall.nft_path` in both firewall modes (external mode still executes this binary for the read-only inspections of FR-FW-2) and, when email is enabled, to `notify.email.sendmail`; executable paths MUST resolve to executable regular files. Ownership validation MUST cover the configured paths and every directory and target traversed through symbolic links, including the parent directories of the targets. These checks apply at startup, on reload and in online `check-config`, before executing a proposed binary, and again before each execution of a configured binary. Failure refuses startup or online `check-config`; a reload is rejected with `reload_failed`, retaining the running configuration (FR-CFG-3). Online `check-config` checks the sendmail path but sends no notification. `check-config --offline` validates syntax and values only, without ownership checks or command execution. A trust failure at submission time is a failed notification and MUST NOT delay routing.
- **FR-CFG-6** 1.x YAML configurations are not read; a 2.0 configuration is written anew, starting from the example (DIST-1). No migration guide or parameter mapping is provided.

## 12. Architecture and implementation

### 12.1 Language and dependencies

- **IMPL-1** Rust, stable toolchain, edition 2024. Every crate of the project MUST declare `#![forbid(unsafe_code)]`; socket options use the safe APIs of `socket2` (`set_mark`, `bind_device`).
- **IMPL-2** Dependencies (netlink links, addresses, routes, rules and notifications, and sockets, confirmed by spikes S3 and S5; nexthop messages implemented in PolyWAN in M2, because `netlink-packet-route` has none): `tokio` (runtime, bounded channels, `AsyncFd` for raw sockets), `netlink-packet-route` for message types and `netlink-proto` / `netlink-sys` for transport, with exact versions pinned because these crates are pre-1.0 (`rtnetlink` at most for connection setup: its builders add duplicate rules on `replace()`, default to protocol `static` and hide header flags), `socket2` with feature `all`, `serde` + `toml`, `clap`, `tracing`, `hyper` 1.x with only the `http1`, `server` and `client` features, `hyper-util` 0.1 with only `tokio`, and `http-body-util` 0.1, all with `default-features = false`: PolyWAN uses hyper's connection APIs with `TokioIo` and `TokioTimer`, without a web framework, for the API sockets, the metrics listener and the CLI's client. PolyWAN builds its own rule and route messages and has no SMTP or TLS dependency (FR-MAIL-1). `nix` with features `user`, `signal`, `fs` and `process` provides safe account lookup, process-group signalling and platform-specific file flags. PolyWAN contains no unsafe code; dependency implementations may contain it.
- **IMPL-3** nftables is driven by generating a ruleset in nft syntax (with all configuration-derived strings validated and every identifier quoted, since names such as `dnat` or `all` are keywords) and applying it with `nft -f -` from the configured `nft_path`, as one atomic transaction, with a 10 s deadline and bounded stderr capture. Rationale: the ruleset depends only on the configuration (FR-FW-5), the same text is what `export-nft` prints, and `nft` is present wherever nftables is used.
- **IMPL-4** Blocking filesystem, sysctl and identity operations, subprocess spawning and supervision, notification formatting, HTTP parsing and response serialisation run outside the routing executor, with bounded concurrency and queues. Status and metrics readers use published snapshots; notifier delivery never applies backpressure to routing. Queues, retained diagnostics and pending retries are bounded in items and bytes.
  Reconciliation preserves the specified operation dependencies: successful nftables application and durable write-ahead persistence precede their dependent mutations. Waiting for these completions MUST NOT suspend State processing of discovery, probe results or routing deadlines. During active operation, independent health decisions and required withdrawals continue within FR-HEALTH-5, without violating reconciliation ordering.
  Completions carry operation and generation identity. Obsolete completions MUST NOT activate paths or commit superseded configuration; uncertain kernel outcomes are observed before dependent work continues. A timeout does not establish cancellation of an in-progress filesystem write. Writes remain serialised, and late completion cannot overwrite newer committed state.

### 12.2 Structure and reconciliation

```text
 netlink events ──► Observer ──┐
                              ├──► State (single owner) ──► Planner ──► Reconciler ──► kernel / nft
 probe results ──► Prober ────┘          │      ▲
                                         │      └── API commands (drain, reload)
                                         └──► Event bus ──► log / email / hooks / API ring buffer / metrics
```

- **Observer**: subscribes to the netlink groups for links, addresses, routes, rules and nexthops on a socket that never sends requests (S3: `netlink-proto` matches replies by sequence number only, so a subscribed socket that also sends requests confuses notifications with replies); dumps and mutations use separate sockets. It performs a full dump after subscribing, buffering the notifications received meanwhile and applying them in order afterwards; on `ENOBUFS` it discards its view and performs a full resynchronisation. Dumps are not consistent snapshots (S3 `dumpskip`): the kernel resumes rule and route dumps by position and never sets `NLM_F_DUMP_INTR` on them, so they can omit or repeat entries under concurrent changes on 6.1 and 7.1, and address dumps miss the flag in a few affected cases. The observer therefore merges dump results by identity (a repeated entry is not an error); retries a dump that carries `NLM_F_DUMP_INTR` (addresses, links, nexthop objects) a bounded number of times, then uses it and schedules a full resynchronisation; abandons a dump that exceeds a deadline and retries it on a new socket; and keeps its dump socket open, reading it with buffers of at least 32 KiB. An entry of its view that no deletion notification removed and that a dump lacks is considered removed only when a confirming read also lacks it: a strict dump filtered to its table for routes, a second dump otherwise; this applies to addresses too. Because the kernel does not notify every removal or nexthop flag change, link or address changes on an uplink trigger re-reads, in both families, of PolyWAN's balancing table, that uplink's path table and the configured discovery tables. Repeated address notifications with unchanged address identity, prefix length, scope and flags do not trigger these re-reads merely because lifetimes changed. Address deletion and changes of flags, including deprecation and DAD state, remain changes. It also receives Router Advertisements on a raw ICMPv6 socket and schedules coalesced discovery-table re-reads and expiry-driven re-reads as specified by FR-DISC-5.
- **Prober**: one task per ready path; reports round results tagged with the path generation (FR-PROBE-3).
- **State**: a single task that owns all mutable state (health state machines, drain flags, configuration, generations) and receives messages from every other component.
- **Planner**: a pure function from (configuration, observed system, health and drain state) to the desired set of artifacts. It contains all the logic of §4 and is unit-tested exhaustively without a kernel.
- **Reconciler**: diffs desired against actual artifacts and applies changes. Each desired state has a generation number; the status API reports the desired and the last fully applied generation.

Reconciliation rules:

- **FR-REC-1** **Cold installation** (no PolyWAN artifacts present), in this order: (1) validate structural settings against the manifest and record the manifest (write-ahead, IMPL-5); (2) sysctls; (3) usable routes of all tables; (4) guard rules of the probe, path and policy-block classes (connections still carrying PolyWAN marks from a previous installation may be rejected by them until step 5 installs their lookup rules; this is part of the installation phase, §4.1); (5) lookup rules in order of decreasing precedence: probe rules, main bypass, path rules, policy rules, `from` rules each followed by its source guard, balancing rule; (6) final guard; (7) nftables table (managed mode), which starts mark assignment. Until step 6 completes, traffic follows either the pre-existing routing or PolyWAN's routing; the invariants of §4.1 hold from the end of step 7.
- **FR-REC-2** **Runtime changes** (health, drain, active set, address, gateway) are applied only through route replacements and deletions and through the addition and removal of `from` rules with their source guards; when an address changes, rules for the new address are added before rules for the old one are removed; a source rule is added before its source guard, and a source guard is removed before its source rule.
- **FR-REC-3** **Adding an uplink** on reload: record its binding in the manifest; its sysctls; its routes; its lookup rules (probe, path, policy, `from` rules each followed by its source guard); nftables table replacement including its assignments; finally its inclusion in the active set and policy tables. **Removing an uplink**: exclude it from the active set and empty its policy tables; nftables table replacement without its assignments; delete its lookup rules, `from` rules and source guards, each source guard before its source rule (connections still carrying its id are now rejected by the path guard); delete its routes. Its id stays reserved (FR-MARK-4). During managed-mode reloads, the assignment dependency applies per path and configured interface. A newly enabled family, or a path moved to another interface, MUST remain excluded from the balancing route and its policy tables until the nftables replacement installing its corresponding assignments succeeds. Its path route and lookup rules precede that replacement. External firewall mode retains the administrator responsibilities of FR-FW-2.
- **FR-REC-4** **Cleanup** (`cleanup`, or `on_shutdown = "cleanup"`) is the reverse of FR-REC-1: nftables table; final guard; lookup rules in order of increasing precedence (each source guard before its source rule); class guards; routes; sysctls restored per §4.6 (only values still equal to what PolyWAN set, using the baseline recorded in the manifest); manifest last. Cleanup is disruptive by definition.
- **FR-REC-5** **Failures**: every step is idempotent; a failed step is logged, counted, reported as an `apply_failed` event with operation, errno and extended acknowledgement, and retried with exponential backoff (1 s to 60 s); steps that depend on a failed step (according to the orders above) are not attempted; retries of an obsolete generation are cancelled when a newer desired generation exists, except that work whose scope the newer generation leaves unchanged (for example one interface's settings, FR-DISC-7) may keep its backoff. The status is `degraded` until the desired generation is fully applied. Because routes and guards precede the lookup rules that use them, and mark assignments follow the lookup rules that interpret them, a generation partially applied during active operation never violates the invariants (§4.1 phases). The API reports a drain or reload as complete only when the applied generation includes it; otherwise the response lists the failed steps.
- **FR-REC-6** **Full reconciliation** (dump of rules, routes and the nftables table, comparison with the desired state, repair following the orders above) runs at startup, every `reconcile_interval` and after any observer resynchronisation. For the nftables table, the comparison uses the JSON listing (`nft -j list table`) recorded right after the last successful application, normalised by removing `metainfo` and every `handle`. Rules are created with `NLM_F_CREATE | NLM_F_EXCL` and never with `NLM_F_REPLACE`, which adds a duplicate rule; the protocol is part of a rule's identity; dumped rules are normalised before comparison (`FRA_SUPPRESS_PREFIXLEN` = `0xffffffff` means unset, a zero mark is dumped with `FRA_FWMASK` only, `unreachable` rules carry table 0); a single-nexthop route equals a one-member multipath route; duplicate entries in a dump are ignored. A PolyWAN artifact that a full reconciliation finds missing is re-created only after the absence is confirmed (§12.2); `EEXIST` when creating a rule with `NLM_F_EXCL`, and `ENOENT` or `ESRCH` when deleting a rule or route, mean that the kernel is already in the wanted state and are neither errors nor repairs. Full reconciliation also inventories the flowtables of every table (FR-CT-2).
- **FR-REC-7** If an internal task terminates unexpectedly, the daemon MUST log the failure and exit with a non-zero status, relying on the service manager to restart it. Warm adoption (FR-REC-8) keeps pinned connections on ready paths unaffected by the restart, provided their artifacts are still intact.
- **FR-REC-8** **Startup classification and warm adoption**: before any mutation, PolyWAN inventories its artifacts (rules and routes in its ranges, the nftables table in managed mode) and validates them against the manifest (IMPL-6). Then:
  - **nothing present**: cold installation (FR-REC-1). Connections may still carry PolyWAN marks from a previous installation; their restoration and path rules route them as before once installation completes;
  - **complete and compatible**: adoption; the differences from the desired state are applied with the runtime and add/remove orders (FR-REC-2, FR-REC-3);
  - **partial** (some kinds missing, possibly with live mark assignments): missing routes and guards are installed first, then missing lookup rules in order of decreasing precedence, then the final guard, and the nftables table last if missing; nothing present and compatible is removed first.

  In external firewall mode, PolyWAN's guarantees begin when both PolyWAN's routing artifacts and the administrator-loaded ruleset are present; until PolyWAN detects the expected table, the status is `degraded` with reason `external_ruleset_missing`.
- **FR-REC-9** **Family handoff**: when the last path of a family is removed: (1) the family's paths leave the active set and policy tables; (2) the shared nftables table is replaced atomically with a version that no longer contains that family's rules, retaining the other family's rules unchanged; (3) that family's rules, guards and routes are removed in the order of FR-REC-4; (4) that family's sysctls are restored to their recorded baselines only where their current values still equal the values PolyWAN set, according to §4.6 and FR-REC-4. The manifest, id reservations, the other family's artifacts and the sysctl baselines still needed are preserved.

### 12.3 State directory, ownership and lifecycle

- **IMPL-5** The state directory (`state_dir`, mode 0700) contains versioned files, each written atomically (temporary file, fsync, rename, fsync of the directory):
  - the **manifest**: structural settings, owned table and priority ranges, protocol, nftables table name, uplink id/name bindings (including reserved ids of removed uplinks), and the **baseline** of every sysctl PolyWAN has changed, recorded the first time PolyWAN changes it and kept across restarts until cleanup. The manifest is written before the kernel objects it describes are created (write-ahead);
  - the **drain state**;
  - the **health checkpoint**: boot identifier (`/proc/sys/kernel/random/boot_id`), `CLOCK_BOOTTIME` timestamp, configuration digest, and per path its identity (uplink id, family, ifindex, source, gateway), state, state-since, hysteresis counters, plus the active set of each family. It is written at every transition and at least every 30 s. A checkpoint is valid only with the same boot identifier, an age under 10 min and the same structural settings; a path's entry is used only if its uplink id, family, ifindex, source and gateway are unchanged, otherwise that path starts cold.
- **IMPL-6** At startup PolyWAN takes an exclusive lock on `/run/polywan/lock`. The lock file MUST be a root-owned regular file with mode 0600, created with those permissions from the outset; an existing file is validated before locking, and symbolic links are refused. The file is never unlinked or replaced while the lock is acquired or released. A second instance, `cleanup`, `forget-uplink` and `notify-test --offline` MUST refuse to run while the lock is held. Then, before any mutation: if the manifest exists, its structural settings MUST equal the configuration's, otherwise startup fails with instructions (run `cleanup`, which uses the manifest, then start with the new settings); if the manifest is missing but PolyWAN-tagged objects exist in the configured ranges, they are adopted only if consistent with the configuration, otherwise startup fails; a corrupt or unknown-version manifest or drain state file makes startup fail unless `run --reset-state` is given. Reset discards drain state and health checkpoints but never the manifest's sysctl baseline unless the manifest itself is unreadable. Other errors reading drain state fail startup. A health checkpoint that cannot be read, decoded or interpreted because of its version is ignored with a warning; all paths then use cold-start initialisation under FR-HEALTH-1, which is an accepted fallback, not equivalent to restoring the checkpoint (a previously unhealthy ready path starts `up`). These validations precede manifest and routing mutations. Untagged objects in the ranges are collisions (FR-ROUTE-6).
- **IMPL-7** On SIGTERM/SIGINT, by default PolyWAN leaves its artifacts in place (`on_shutdown = "keep"`), so that a restart or upgrade causes no outage; `on_shutdown = "cleanup"` removes them (FR-REC-4). `cleanup` uses the union of the manifest and the configuration, so that a changed configuration does not hide old artifacts: it evaluates each layout with its corresponding route protocol, removes their union without removing differently tagged objects, and applies FR-REC-4 to the combined cleanup. The manifest is removed only after all cleanup steps succeed.
- **IMPL-8** No panics in the daemon path: every fallible operation returns an error handled by the caller (FR-REC-5, FR-REC-7).
- **IMPL-9** Resource targets on a Raspberry Pi 4 with 4 uplinks, default settings and a release build, measured over 10 min excluding hook processes: under 1% of one CPU core on average, under 30 MB RSS.

### 12.4 Security

- **IMPL-10** The provided systemd unit MUST use sandboxing (`NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK`, `CapabilityBoundingSet=CAP_NET_ADMIN CAP_NET_RAW CAP_SETUID CAP_SETGID CAP_KILL CAP_CHOWN`, `SystemCallFilter=@system-service`) and `Restart=always` with `RestartPreventExitStatus=78`; `CAP_CHOWN` assigns the configured groups of the API sockets. The unit uses `StateDirectory=polywan`, `StateDirectoryMode=0700`, `RuntimeDirectory=polywan`, `RuntimeDirectoryMode=0755` and `RuntimeDirectoryPreserve=yes`, owned by root. These directories remain writable under `ProtectSystem=strict`; additional configured paths require explicitly provisioned directories and appropriate sandbox exceptions. Service stop, failed startup and restart MUST NOT remove or replace the instance lock or its parent directory (IMPL-6). Socket removal and replacement remain subject to FR-API-1. The unit uses `KillMode=mixed`: initial SIGTERM targets the daemon, allowing its bounded email flush (FR-MAIL-3); remaining processes are killed when the daemon exits or the stop timeout expires. The packaged defaults are `TimeoutStartSec=90s`, `TimeoutStopSec=30s` and `RestartSec=5s`. A stop timeout can interrupt cleanup; an existing manifest is retained until cleanup succeeds, and the documentation explains recovery. The unit is ordered after `nftables.service` and `network.target`.
  The unit uses `Type=notify` with `NotifyAccess=main`. `ExecReload=` runs `polywan reload`. It succeeds only after the daemon confirms application of the new configuration, and fails on rejection, partial application, application not confirmed within the request deadline, or unknown outcome (FR-API-3, FR-CFG-3). Failure does not imply rollback. A non-default `api.socket` requires a drop-in replacing `ExecReload=` with the corresponding `--socket`; the documentation shows the replacement and `daemon-reload` procedure. SIGHUP keeps working. A reload that changes the control socket's path or access closes the requesting connection when it commits, before the answer (FR-API-1): `polywan reload` then reports that the outcome is unknown and exits with status 1, and the `config_reloaded` or `reload_failed` event records the outcome; the documentation recommends a restart for such changes. When `NOTIFY_SOCKET` is set, except in `--dry-run`, PolyWAN sends `READY=1` once its API listeners are open and its initial reconciliation attempt has reached either completion or a reported failure. It MUST NOT notify readiness while operations belonging to that attempt remain in flight. The published status reflects that outcome. Readiness does not require healthy uplinks or successful installation of every artifact; failed application remains degraded and is retried. PolyWAN also sends `STATUS=` with a one-line summary on changes of status or active sets, and `STOPPING=1` at shutdown; it uses the notification protocol directly, without linking libsystemd, and behaves the same without systemd. The runtime directory is owned by root with mode 0755; the state directory keeps mode 0700 (IMPL-5). Acceptance tests MUST run against this unit (AS-34).
  Email MUST NOT weaken the default sandbox. The reference configuration is msmtp (`/usr/bin/msmtp` as `notify.email.sendmail`) with its system configuration readable inside the unit. The documentation distinguishes argument compatibility from operation tested under the complete sandbox, naming the distribution, package version and configuration of every tested alternative; a generic `NoNewPrivileges=no` and writable-spool drop-in MUST NOT be presented as sufficient (with `SystemCallFilter` and without `CAP_SYS_ADMIN`, systemd implies `NoNewPrivileges` anyway).
- **IMPL-11** The control socket is the only API control surface; the status socket and the metrics endpoint are read-only. Root-only lifecycle commands and signals keep their specified behaviour. Every listener enforces an explicit endpoint allowlist before any side effect. Notification-test results and command diagnostics are available only through the control socket and protected logs. `run --dry-run` opens no API or metrics listener and executes neither hooks nor sendmail.

## 14. Verification

Correctness of a routing daemon can only be demonstrated by moving packets; acceptance is defined by tests.

### 14.1 Test levels

1. **Unit tests**: configuration parsing and validation, mark allocation, health state machine (with deterministic, synthetic probe results), active set decision table, planner output (golden tests on the desired artifacts for representative configurations), nftables generator output (golden tests).
2. **Integration tests in network namespaces**: a harness builds the topology of §14.2 with namespaces and veth pairs, runs the real binary in the router namespace and checks real traffic. They MUST run in CI on every push, on two environments: the CI runner's current kernel with a current nftables, and a virtual machine booted with the minimum supported kernel (6.1) and nftables (1.0.6), for example with virtme-ng.

### 14.2 Reference topology

An "internet" node hosting the probe targets (including the addresses of the default targets) and test servers for both families; three "provider" nodes (plain routing with DHCPv4/DHCPv6/RA; CGNAT; PPPoE); the router under test; a LAN client. Addresses use documentation and benchmarking prefixes (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `198.18.0.0/15`, `100.64.0.0/10`, `2001:db8::/32`). Failures are injected with `ip link`, nftables rules with deterministic patterns (for example dropping every third probe) and, for statistical scenarios only, `tc netem`.

### 14.3 Acceptance scenarios

Each scenario runs for IPv4 and for IPv6 unless stated otherwise, always with operating-system default routes present in the main table, so that leaks are observable. Results are measured on egress packets and flow continuity, not only on routing state. Rejection is verified by the absence of egress packets, not by the error seen by the client: the kernel rate-limits the ICMP errors of `unreachable` rules per source host with host-wide sysctls (`net.ipv4.route.error_cost`, `error_burst`), and a client can miss an error that arrives while `connect()` holds the socket (S2, harness). Time limits are measured from the injected kernel event to the observed route change. Statistical scenarios use five independent samples, each containing 1000 connections with distinct 5-tuples to at least 50 destinations; the 5-tuples of each sample differ by the source ports the kernel picks (the multipath hash key is random per boot before Linux 6.11, so a sample cannot be replayed across boots). For each scenario, family, mark mask and environment separately, the stated share range applies to the aggregate 5000 connections. Each sample must additionally satisfy a range with twice the stated half-width around the same centre: AS-01 requires 45–55% aggregate and 40–60% per sample; AS-02 requires 70–80% aggregate and 65–85% per sample. Bounds are inclusive. Per-sample counts are recorded. Connection-success, permitted-egress, continuity and no-leak requirements apply to every sample and are not averaged.

## 15. Spikes before implementation

Short, throw-away experiments (network namespaces or disposable virtual machines) that MUST be completed, with results written down, before the corresponding code is written. Each spike runs on Linux 6.1 with nftables 1.0.6 and on the latest stable kernel.

- **S1** Routing core: the rule layout of FR-ROUTE-3 with guard rules, encoded marks and zero-field source selectors, including device-bound lookups (`SO_BINDTODEVICE`) with empty tables and with a competing main default; IPv4 and IPv6 inline multipath updates, including IPv6 intermediate states and failures (FR-ROUTE-2) and IPv6 point-to-point members with link-local gateways (single → multiple → single); layer-4 hashing distribution; pinning of marked connections across updates; the activation, retirement and cleanup orders of FR-REC-1, FR-REC-3 and FR-REC-4 with traffic checked at every intermediate state; the startup cases of FR-REC-8 (intact artifacts with an expired checkpoint, partial artifacts with a recent checkpoint, preloaded external ruleset); local source address selection for unbound router traffic over a multipath route, for both families, including the FR-DISC-6 configuration.
- **S2** Mark lifecycle: the chains of §4.7 with constant-only mark operations; preservation of foreign bits; retransmitted SYNs, one-way UDP, RELATED ICMP; output route chain rerouting; `rp_filter = 2` + `src_valid_mark = 1` behaviour of AS-30.
- **S3** Rust netlink: create, dump, replace and delete rules and multipath routes, and receive notifications, with `rtnetlink`/`netlink-packet-route`; identify missing features and decide between upstream contributions and a bounded local implementation.
- **S4** Coexistence and control plane: `suppress_prefixlength 0` with DHCP- and RA-installed default routes in main, with systemd-networkd and NetworkManager; effect of systemd-networkd's foreign-object management settings; every item of FR-CT-5 starting from no lease, no global address, no default route and an empty active set, with all guard rules installed.
- **S5** Probes with `SO_BINDTODEVICE` + `SO_MARK` + bound source from Rust, ICMP and TCP, both families, with reply validation.

All five spikes were completed on Linux 6.1.0-53 with nftables 1.0.6 and on Linux 7.1.13 with nftables 1.1.3 (S4 also on 6.12 virtual machines); scripts, results and findings are in `spikes/`. Their conclusions are incorporated in v0.6.

## 16. Distribution and repository

- **DIST-1** Release artifacts: static binaries for every PLAT-3 target, `.deb` packages (systemd unit, `polywan` group, example configuration, man page), SHA-256 checksums, signed with GitHub artifact attestations. The example configuration is installed as `/usr/share/doc/polywan/examples/config.toml`, not as an active `/etc/polywan/config.toml`; it is the text `generate-config` prints and stays minimal (two uplinks), while the recipes of DIST-3 carry fuller configurations (more uplinks, a DMZ, policies, notifications). The package creates the `polywan` group when it is configured and installs the unit without enabling or starting it; upgrades keep the administrator's enablement and masking and restart only a running daemon. Service actions honour local service policy. Removal requests service stop and attempts `cleanup` with the default configuration before removing the executable. Cleanup is skipped when the daemon remains running or the installation environment cannot safely operate on the target system's networking. Failure, skipped cleanup or missing configuration is reported with recovery instructions, without preventing removal. Purge deletes `/var/lib/polywan` only while excluding concurrent PolyWAN lifecycle operations and after establishing that no manifest exists; otherwise, including a corrupt or dangling manifest or an inspection error, it preserves the directory and reports why. Purge never follows a state-directory symbolic link to delete its target, deletes `/etc/polywan`, or deletes configured paths elsewhere. Installations with a non-default configuration path must stop the daemon and run `cleanup` before removing the package.
- **DIST-2** The project is named PolyWAN, formerly Fault Tolerant Router (renamed in v0.11, before any 2.0 package, crate publication, unit file or API path existed). Crate, binary and Rust library identifier are named `polywan`; configuration, state and runtime paths, the nftables table, the API group, environment variables and metric names use the same name. Packages do not ship an alias with the old name. The license is `MIT OR Apache-2.0` (the Rust ecosystem's convention: MIT's simplicity with Apache-2.0's explicit patent grant); `LICENSE-MIT` and `LICENSE-APACHE` replace `LICENSE` on the `v2` branch, contributions are accepted under the same dual license, and the README states that 1.x was GPL-2.0.

## 18. Decisions log

- **Q1 (name)** — Decided: `fault-tolerant-router` for crate and binary, no short alias shipped (DIST-2). Amended in v0.11: renamed PolyWAN (`polywan`) before the first 2.0 package, so that no published name, path or API changes after the release; the GitHub repository is renamed in place (DIST-4).
- **Q2 (license)** — Decided: MIT for 2.0; 1.x stays GPL-2.0 on `legacy/ruby`. Amended in v0.10: `MIT OR Apache-2.0`, adding Apache-2.0's explicit patent grant; a GPL-2.0-only project can still use the code under MIT. 2.0 reuses no 1.x code, and the only external 1.x contribution is a 4-line change to a configuration template.
- **Q3 (IPv6 NAT default)** — Decided: no default; explicit choice required (FR-NAT-1).
- **Q4 (mask size)** — Decided: 8-bit field, 2-bit class + 6-bit id, up to 63 uplinks (FR-MARK-2).
- **Q5 (drain persistence)** — Decided: persisted (FR-SEL-3).
- **Q6 (automatic delegated prefix)** — Decided: out of scope; IPv6 prefix translation deferred entirely (§1.3).
- **Q7 (minimum kernel)** — Decided: Linux 6.1 and nftables 1.0.6 (Debian 12 baseline) instead of 5.15, to reduce the compatibility matrix for a release planned for October 2026.
- **Q8 (nexthop objects)** — Decided: inline multipath routes in 2.0 (FR-ROUTE-2), with an operational (not atomic) update requirement for IPv6; PolyWAN owns no nexthop objects (future work). Amended after S4: discovery resolves single, non-group nexthop objects (FR-DISC-3), because systemd-networkd uses them for Router Advertisement routes (observed with 257; option introduced in 256).
- **Q9 (termination)** — Decided: guard rules with action `unreachable` per mark class plus a final guard, instead of terminal routes in each table (FR-ROUTE-1). Consequence: while PolyWAN is installed, default routes of the main table are never used for traffic that enters PolyWAN's rule sequence, including router-originated traffic. Corrected after S1: the original rationale (route-level rejects are skipped by device-constrained lookups) applies equally to rule-level rejects for IPv4 (§4.1.1); guard rules are kept for class fallthrough and a single final guard.
- **Q10 (policy fallback)** — Decided: policy-balance tables fall through to the balancing rule instead of copying the balancing route (FR-ROUTE-1).
- **Q11 (drain and bound traffic)** — Decided: router-originated traffic explicitly bound to an uplink address is not affected by drain (FR-SEL-3).
- **Q12 (IPv6 next hop)** — Decided: every IPv6 path needs a gateway address, also on point-to-point links (FR-DISC-3). Confirmed experimentally: the kernel rejects device-only members in IPv6 multipath routes.
- **Q13 (managed families)** — Decided: PolyWAN installs artifacts only for families enabled on at least one uplink, and hands a family back to the operating system when its last path is removed (§4.3).
- **Q14 (guarantee phases)** — Decided: invariants hold during active operation; installation, repair and cleanup have their own, weaker guarantees (§4.1).
- **Q15 (control plane)** — Decided: no pre-emptive exemptions from the guard rules for control traffic; spike S4 determines whether any are needed (FR-CT-5). Confirmed by S4: none is needed. Following M2: retain the guard layout without control-plane exemptions; FR-CT-5 explicitly limits compatibility for legacy DHCPv6 Server Unicast traffic as well as the existing DHCPv4 renewal case. PolyWAN does not learn DHCPv6 server-to-uplink associations or steer these messages specially; DIST-3 MUST document the consequences and remedies.
- **Q16 (IPv6 multipath update)** — Decided after S1: keep `NLM_F_REPLACE` and document the empty-table outcome of a failure after the first insertion (FR-ROUTE-2). Alternative considered: make-before-break with metrics 100 and 101 alternating (verified to work); rejected because it holds two routes during each update and its deletion step exposes subsets of the previous set rather than of the target set.
- **Q17 (traffic bound to an interface)** — Decided after S1 and S5: router-originated traffic bound to an interface is an explicit decision, treated like address binding and excluded from INV-3 and INV-4 (§4.1.1); the kernel leaves no alternative for IPv4. M2 clarified that IPv6 source selection after a failed interface-constrained lookup need not select an address of the bound interface; the guarantee remains egress isolation, not connectivity.
- **Q18 (email submission)** — Decided in v0.11: the system's sendmail interface with explicit recipient arguments, without `-t`, instead of a built-in SMTP client (FR-MAIL-1). PolyWAN keeps message construction, coalescing, bounded retries and rate accounting; submission runs as root through a trusted executable inside the unchanged sandbox, with msmtp as the reference configuration. Successful submission does not establish delivery. Notification tests run through the daemon's control socket; offline testing is explicit.
- **Q19 (HTTP stack)** — Decided in v0.11: `hyper` 1.x with the HTTP/1 server and client, `hyper-util` with the tokio adapters and timer, and `http-body-util`, without a web framework (IMPL-2). Connection, input, output, time and admission limits are enforced separately (FR-API-4). A minimal server and client measured 0.53 MB larger with this stack (x86_64 musl, stripped); IMPL-9 and INV-8 are established on the integrated daemon.
- **Q20 (read-only API access)** — Decided in v0.11: separate control and status Unix sockets (FR-API-1). The status socket is open to local users by default, can be restricted to an existing group or disabled, and exposes only the documented operational status and events; separate listener capacity and bounded work protect the control socket and routing. Filesystem permissions were preferred to peer-credential authorisation (`SO_PEERCRED`, `SO_PEERGROUPS`) because the policy stays visible in the file system.
- **Q21 (user interface)** — Decided in v0.13, after a review of the interface against 1.x habits with the external reviewer: 2.0 keeps the purpose and philosophy of 1.x, not its interface. No configuration version key (FR-CFG-1) and no migration guide (FR-CFG-6); the example configuration is a packaged file, which `generate-config` prints for installations from the static binary (DIST-1); the nftables text follows `nft list ruleset` and carries persistent `comment` attributes (FR-FW-3); events are also available as JSON lines and the human status shows readiness and active-set membership (§9); systemd readiness, synchronous reload and a configuration exit status (IMPL-10). Kept as they are: the flat command vocabulary, `[[uplink]]` with stable numeric ids (they encode connection identity), the compact probe target and duration strings, the file locations, the `/v1` API and the separate control and status sockets. Native journal fields are future work (§13).
