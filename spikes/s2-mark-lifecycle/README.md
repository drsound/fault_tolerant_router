# S2 — Mark lifecycle

Spike S2 of SPEC.md §15: the chains of §4.7 with constant-only mark operations, preservation of foreign bits, retransmitted SYNs, one-way UDP and RELATED ICMP, output route chain rerouting, policies at kernel level, and the reverse-path filtering behaviour required by AS-30 (`rp_filter = 2` with `src_valid_mark = 1`). A second round covers the original-direction condition of the postrouting assignment (AS-50, `t8`), the multicast and broadcast skips (`t9`) and software flowtables (FR-CT-2, AS-33, `t10`).

## Environment

Both environments of `spikes/README.md`: Debian 12 with Linux 6.1.0-53 and nftables 1.0.6; Debian 13 with Linux 7.1.13 and nftables 1.1.3. Every test ran on both; full logs are in `results/linux-6.1.txt` and `results/linux-7.1.txt`.

## How to run

As root on a disposable Linux host with iproute2, nftables, conntrack, tcpdump, nstat and python3: `./run.sh`, or one test with `bash tN-name.sh`. The tests create namespaces named `s2-*` and remove them on exit. They reuse the topology of `../lib/netns.sh` (described in `../s1-routing-core/README.md`) and the FTR rules and routes of FR-ROUTE-3. `s2lib.sh` holds the refined ruleset generator (`s2_nft_text`), an observation table that counts the packets of one connection after each FTR chain, split by conntrack direction, by the FTR field of the packet mark and of the conntrack mark, and by egress interface (`chk_up`/`chk`), and the administrator's port forwarding used by several tests. `s2tool.py` adds traffic modes to `../lib/peer.py`: unanswered SYNs, one-way UDP streams, bulk transfers, raw-socket ICMP probes, datagrams with a given TTL, datagrams to broadcast and multicast destinations out of a given interface, and a multicast routing entry (`MRT_INIT`/`MRT6_INIT` with one input and one output interface) for routed multicast.

## The ruleset

`s2_nft_text` implements §4.7 with these refinements over the draft used in S1: untracked packets are skipped in every chain and non-unicast packets in prerouting (`meta pkttype != host`) and postrouting (multicast and broadcast destinations), as §4.7 and §4.8 restrict marking to tracked unicast traffic; policies are prerouting rules that write the policy value into the packet mark only and end with `return`; the postrouting assignment rules carry `ct direction original` (§4.7 step 3.2, added in the second round and tested by `t8`; t1–t7 were re-run with it). Environment variables of `s2_nft_text` select control variants: `S2_NO_OUTPUT`, `S2_NO_DIRECTION`, `S2_NO_NONUNICAST`, and `S2_NONUNICAST_ADDR` for the address-based skips proposed in F12. Per family and configuration it has 151 rules for three uplinks: 63 restoration rules in prerouting and 63 in output (every path value, FR-MARK-3), one inbound assignment rule per uplink, the policies, the probe-class skips, one outbound assignment rule per uplink in postrouting, and the NAT chain. Chain types and priorities: filter/prerouting −150, route/output −150, filter/postrouting −150, nat/postrouting 100.

## Findings

### F1. Constant-only mark operations, no verdicts (FR-MARK-3, FR-FW-4)

Both nftables versions accept the ruleset. The netlink bytecode (`nft --debug=netlink`) contains 272 bitwise operations, all of the form `reg = (reg & constant) ^ constant`; none combines two registers. `meta mark set meta mark & 0xff00ffff | 0x00010000` compiles to `[ meta load mark => reg 1 ] [ bitwise reg 1 = ( reg 1 & 0xff00ffff ) ^ 0x00010000 ] [ meta set mark with reg 1 ]`, and `ct mark set …` to the same with `ct load`/`ct set`, so FR-MARK-3 is met on nftables 1.0.6 and kernel 6.1. The rules use no verdict other than `return`; the only `accept` is the chain policy.

### F2. Lifecycle per packet (§4.7, FR-MARK-5, FR-POL-2)

Observed after each FTR chain for both families (`t2`):

- outbound forwarded connection: the first packet is unmarked in prerouting (no assignment before routing); after postrouting every packet carries the egress path in both the conntrack and the packet mark; every later packet in both directions is restored in prerouting;
- policy-marked connection: the first packet carries the policy value (`0x81`) in the packet mark only, never in the conntrack mark; after postrouting the conntrack mark holds the path value of the actual egress (1), not the policy value; with the policy table of A empty the connection is balanced through B and gets path 2 (FR-POL-2);
- inbound connection through B with active set {A}: every packet in the original direction, the first included, carries path 2 after prerouting; every reply is restored when it enters from the downlink and leaves through B (INV-5);
- ICMP and TCP probes of A with active set {B}: the probe value survives the output route chain and postrouting, so it is never replaced by a path value; probes leave through A; the conntrack entries of probes carry no path value; replies to probes enter unmarked, as §4.7 1.2 states.

### F3. Foreign bits and other mask positions (FR-MARK-1, INV-7, AS-24, AS-43)

Another table writes packet bits outside the FTR field before FTR's prerouting chain and after FTR's prerouting and postrouting chains, conntrack bits on new connections in prerouting and output, and a probe socket carries foreign bits in `SO_MARK`. With `fwmark_mask` at bit offsets 0, 16 and 24, for both families (`t3`): outbound and inbound connections and probes use the intended uplink; every packet leaves with all foreign bits and the expected FTR value; the conntrack mark ends up as foreign bits | path value (probes: foreign bits only). Routing rules with mask selectors ignore the foreign bits.

A table that writes the conntrack mark at priority −200 in prerouting or output, the same priority as connection tracking, may run before the conntrack entry exists (`ct state new` did not match on either kernel); at −190 it works. The nftables documentation lists the conntrack priority but does not define the order of hooks registered at the same priority; the documentation for administrators (FR-FW-6) should say that rules relying on conntrack must use a priority above −200.

### F4. AS-22: unanswered SYNs and one-way UDP

Ten unanswered TCP connections and ten one-way UDP flows per family ran for 8 s while the active set changed five times, including to the empty set (`t4`). All 40 flows were seen, and every packet of every flow left through a single uplink (captured on all uplinks, grouped by flow). Every SYN flow sent at least 4 SYNs on 6.1 (0, 1, 3, 7 s) and 7 on 7.1, whose default `tcp_syn_linear_timeouts` makes the first retransmissions linear. Restoration happens for every packet regardless of conntrack state, so retransmitted SYNs follow the first one.

### F5. RELATED ICMP and path MTU discovery (AS-31 core)

With active set {A} and inbound UDP through B to a closed port of a LAN host (via the administrator's port forwarding), the host's port-unreachable and the router's own time-exceeded (inbound packet arriving with TTL 1) both leave through B only, for both families (`t4`); the router-generated error is RELATED to the inbound connection, gets path 2 from the output route chain and is translated back to B's address. For path MTU discovery, a 1300-byte link inside provider A makes A answer the client's full-size segments with "fragmentation needed" / "packet too big"; a 300 kB transfer pinned to A completes after A leaves the active set, and with those ICMP errors dropped on the router a new transfer fails (control). RELATED errors are thus delivered through restoration and conntrack NAT.

### F6. The output route chain is necessary (§4.7 step 2)

Provider A routes to the router an address configured on another interface, so no source rule applies to it. With active set {B}, the router's replies to connections that arrived through A leave through A, because the output route chain restores path 1 and the mark change triggers a new routing decision. Without the output chain (control), the same replies follow the balancing route through B (`t5`, both families). The nftables documentation states that the `route` chain type exists only for the output hook and reroutes when the mark changes, which matches.

### F7. Policies at kernel level (AS-15 core)

With policies to A, fallback balance on TCP port 7 and fallback block on TCP port 8, and active set {B, C} (`t6`, both families): new policy connections use A although A is not in the active set; with A's policy tables emptied (A unhealthy or drained), flows opened before stay alive on A, new balance-policy connections are balanced over B and C, and new block-policy connections fail without any packet leaving any uplink; a flow opened during the fallback stays on its uplink after A's tables come back, while new connections return to A.

Clients do not always see an immediate error for blocked connections, for two reasons outside FTR: IPv4 errors for input-route rejections are rate-limited by the kernel per source host (`net.ipv4.route.error_cost` and `error_burst`, 1 per second after a burst of 5, counted as `IcmpOutRateLimitHost`); and a Linux client that receives the error while `connect()` still holds the socket lock ignores it (`TcpExtLockDroppedIcmps`) and reports `ENETUNREACH` only when the retransmitted SYN triggers a second error. Acceptance tests must therefore check rejection by egress counters, not by client errors within one second.

### F8. AS-30: replies with an empty active set and no default route

With every main default route removed (including the one through the unmanaged uplink) and the active set empty, all of the following are accepted, for both families (`t7`): inbound DNAT traffic, connections to a router listener, ICMP probe replies and TCP probe replies, with no IPv4 reverse-path drop. IPv4 negative control: removing the source rule of the probe source makes ICMP probe replies fail the reverse-path check, whether the source guard is still present or not (`TcpExtIPReversePathFilter` increments); TCP probe replies fail likewise. With `src_valid_mark = 0` on the uplinks, inbound DNAT traffic is dropped by the IPv4 reverse-path check (its path mark is ignored and the check runs against the post-DNAT destination, which has no source rule), while connections to router addresses and probe replies still pass through the source rules. FR-SYS-2's combination is therefore required for inbound port forwarding and sufficient for the rest; its stated dependency of probe replies on the source rules is confirmed.

### F9. JSON listing and atomic replacement (FR-REC-6, FR-FW-1)

After re-applying identical text with the replacement transaction (`add table`, `delete table`, full table), the JSON listing (`nft -j list table`) differs only in the table handle; rule and chain handles restart from the same values in the new table. After removing the `metainfo` object and every `handle` key, the listings compare equal, and a rule added by a third party is detected. FR-REC-6 should state this normalisation. This is an experimental result: the nftables documentation describes the JSON export but not the stability of handles. Twenty consecutive replacements, alternating two different versions of the table, did not disturb a running masqueraded outbound flow or an inbound DNAT flow (gaps under 0.5 s, no error), for both families.

### F10. Smaller observations

- `all` and `dnat` (S1) are nftables keywords and break the parser when used as identifiers; the generator must quote every name it emits (IMPL-3).
- Flowtables were not exercised in the first round (documentation only); F13 and F14 replace that note.

### F11. Postrouting assignment only in the original direction (AS-50, §4.7 step 3.2)

A remote host behind the unmanaged interface `wanx` opens connections to the router's `wanx` address and to the LAN host; its address is reachable only through the balancing table, so with active set {A} the replies leave through A (`t8`, both families). With `ct direction original` on the postrouting assignment rules, every reply leaves through A with an empty FTR field in the packet and conntrack marks (IPv4 forwarded case: `r_post_all=9 r_post_c0=9 r_post_m0=9 r_fin_if_wana=9`), no original packet is ever marked and the conntrack entries carry no path value. Such connections are not pinned: a long flow from the remote host to the LAN host survives the active set changing to {B} and A's path table being emptied (A not ready), its replies following the balancing route to B (31 replies through B, none through A, no error). The controls behave as in F2 with the amended rules: outbound connections from the LAN get path 1 in postrouting with the first packet unmarked in prerouting, inbound connections through B get path 2 on every original packet, ICMP and TCP probes keep the probe value and their conntrack entries carry no path value.

Negative control, without the direction condition: the first reply is assigned path 1 (`r_post_c1 = r_post_all`), the conntrack entries carry 0x1, later original packets are restored to path 1 in prerouting (12 of 15) and the router's replies in the output chain. The long flow is then pinned to A although FTR never chose A for it: when A stops being ready its replies hit the path guard and the flow fails (7 of 26 lines answered, timeout, nothing through B) while B was available. The condition is therefore required: without it, any connection whose first reply happens to be balanced through an uplink becomes pinned to that uplink and is cut when it stops being ready. The replies of unassigned connections are not translated (NAT applies only to the original direction of connections from downlinks), so moving them between uplinks works only where the remote network accepts asymmetric routing, as in the test.

### F12. Multicast and broadcast skips (§4.7, §4.8)

`t9` sends UDP datagrams in 32 cases with three generators: the current one (`meta pkttype != host` in prerouting, `ip daddr { 224.0.0.0/4, 255.255.255.255 }` and `ip6 daddr ff00::/8` in postrouting), none of the skips (control) and the address-based skips proposed below. The LAN has a policy on the test ports, so a missing skip shows up as the policy value 0x81 or as a path value. The pkttype column is what an nftables counter saw after FTR's prerouting / postrouting chain ("–": the packet does not traverse that hook). The router looped back a copy of its IPv4 broadcasts and, with the multicast routing socket of the test open, of its IPv6 multicasts. Values are the FTR values found in any packet or conntrack mark; identical on both kernels and both nftables versions.

| provider A to 255.255.255.255, 192.0.2.255, 224.0.0.251, ff02::fb on `wana` | broadcast or multicast / – | – | 1 | – |
| provider C to 224.0.0.251, 255.255.255.255, ff02::fb through the GRE uplink `wanc` | **host** / – | **3** | 3 | – |

Observations:

- `meta pkttype` is the link-layer classification. Forwarded unicast is always `host` (the kernel forwards only packets addressed to the router's link-layer address), so the prerouting check never skips forwarded unicast; the controls are marked by every generator.
- A tunnel uplink delivers multicast and broadcast as `host`: GRE decapsulation (`ip_tunnel_rcv`) ends with `skb_scrub_packet`, which resets the packet type (kernel source, v6.1). The current generator therefore assigns path 3 to multicast and broadcast arriving through `wanc`. The same is expected for other uplinks without link-layer addresses (PPP, WireGuard, tun); not tested.
- In postrouting `meta pkttype` is `host` for every packet the router generates, including broadcasts and multicasts, and forwarded packets keep their input type (routed multicast: `multicast`). Postrouting must therefore rely on destinations. The current destination checks are not equivalent to the prerouting check: they cover multicast and the limited broadcast but not subnet-directed broadcasts, which depend on the addresses configured at runtime. A directed broadcast sent by the router out of an uplink, and one forwarded from the LAN with `bc_forwarding`, are assigned the uplink's path.
- The router's own broadcasts and multicasts are looped back and traverse prerouting with the egress interface as input interface; nftables reports their type as `broadcast` or `multicast`. Without the skip, the LAN copy matched the policy; on an uplink it would match the inbound assignment. Both the current and the proposed generator skip them.
- A unicast packet on an L2 broadcast or multicast address is not `host` and is never assigned. UDP to the router is answered (the reply leaves through A by the source rule, unassigned); TCP to the router and port forwarding fail with or without FTR, because the kernel accepts TCP and forwards only packets whose type is `host`. Nothing more is needed for this case.
- Effect of the gaps: none on routing. A non-unicast conntrack entry receives no reply in its reverse tuple, so a path value only labels the entry (and would count in per-path accounting). The gaps contradict the statement of §4.7 that only unicast traffic is marked.
- Proposed rules (`S2_NONUNICAST_ADDR=1`), which leave all 32 cases unmarked and keep the controls marked on both environments: in prerouting, after the restoration rules and before the inbound assignment, `ip daddr { 224.0.0.0/4, 255.255.255.255 } return`, `ip6 daddr ff00::/8 return` and `meta nfproto ipv4 fib daddr type broadcast return`, keeping `meta pkttype != host return`; in postrouting, after `ct mark & mask != 0 return`, `meta nfproto ipv4 fib daddr . oif type broadcast return`. The `fib` expressions classify the address with the kernel's address-type lookup, not with the routing rules; placed after the restoration and after the conntrack mark check, they run only for packets of connections without a path. Both nftables versions accept `fib daddr . oif type` in a postrouting chain.

### F13. Software flowtables (FR-CT-2, AS-33)

`t10` adds an administrator's table with a flowtable (`hook ingress priority 0`) and a forward chain with `meta l4proto { tcp, udp } flow add @ft`, and runs long TCP flows (10 lines per second each way) from a unique client port: outbound from the LAN host via A, inbound from the internet through B's port forwarding to the LAN host, and between the LAN and a second downlink `dmz`. It counts the flow's packets after FTR's chains, at the netdev egress hook of every interface split by empty or set FTR field in the packet mark, and reads the offload flag and the FTR field of the conntrack entry; phases of 1.5 s: steady state, active set change, path not ready (route withdrawn). Results were identical on both kernels and both families.

- Baseline without flowtable: every packet traverses FTR's chains and leaves with the FTR field set; when the pinned path stops being ready the flow fails at the path guard, never moved.
- Flowtable with `lan`, `wana`, `wanb`: the handshake (3 packets) traverses FTR's chains and is assigned; the conntrack entry is then flagged `OFFLOAD` and keeps the path value. In steady state no packet of the flow traverses FTR's prerouting or postrouting chain (`ftr_pre=0 ftr_post=0` while 16 packets leave through `lan` and 32 through `wana`), and every offloaded packet leaves with an empty FTR field in the packet mark (`wana_z=32 wana_m=0`), outbound and inbound, both families.
- Active set change: the offloaded packets stay on the pinned uplink. For IPv4 exactly one packet traverses FTR's chains after the change (restored, routed through the same uplink) and the flow is offloaded again; for IPv6 nothing changes. Consistent with the kernel: the flowtable re-validates the cached route of every packet (`nf_flow_dst_check`) and tears the entry down when it is stale, returning the packet to the classic path (kernel source, v6.1); an IPv4 routing change invalidates every cached IPv4 route, while an IPv6 cached route stays valid unless its own table changes.
- Path not ready (route withdrawn): the flow fails as in the baseline, with the packets rejected by the path guard (outbound; ICMPv6 errors counted, IPv4 errors rate-limited as in F7) or dropped by the reverse-path check (inbound). The entry is torn down in every case except one: with the downlink-only flowtable, the IPv4 inbound entry keeps its `OFFLOAD` flag after the withdrawal, on both kernels. The checks labelled "never moved" assert only that the client's flow times out; they do not count egress packets on the other uplinks, and they are not synchronised with the moment of the routing change, so they do not prove the absence of misrouting.
- Flowtable with downlinks only (`lan`, `dmz`): traffic between the two downlinks is offloaded in both directions without involving FTR, as intended, but the LAN-ingress direction of uplink traffic is offloaded too: the original packets of outbound flows and the replies of inbound flows bypass FTR's chains and leave the uplink with an empty FTR field, while the other direction (uplink ingress, not hooked) traverses the chains. Pinning behaves as above.

Interpretation. The reason given by FR-CT-2 is accurate: offloaded packets bypass the hooks of §4.7, so FTR does not restore their packet-mark field (an empty field was observed in this setup; that the fast path clears it in general is not established), and every other netfilter hook of the classic path is skipped too. In the tested TCP flows and operations (active set change, withdrawal of the path route) the flows kept their uplink, because offload starts after FTR has assigned the path and the flowtable re-validates the routes it cached per packet (`nf_flow_dst_check`, kernel source). That is less than the INV-2 contract: t10 did not test the replacement of a path route's gateway or source, the removal of lookup rules while the path route remains (FR-REC-3 intermediate states, AS-37), the insertion of a main route that should take over through the main bypass (INV-1), policies, drain, UDP or reverse-path enforcement on fast-path hits, and validating a cached destination is not the same as re-running the rule sequence. Kernel source of 6.1 also shows that destination validation is skipped for the direct transmit mode (`FLOW_OFFLOAD_XMIT_DIRECT`), which bridged setups can select without hardware offload. A flowtable with only downlinks bypasses §4.7 for one direction of every flow between that downlink and an uplink. Not tested: hardware offload (`flags offload`). Analysis only, not observed: the reverse route lookup is constrained to the input interface, so for IPv4 a lookup that fails at an FTR guard would fall back to an on-link route (§4.1.1) instead of a rejection.

Conclusion: these results do not justify relaxing FR-CT-2. The refusal stays, extended to flowtables that list downlinks; a relaxation would first need the tests listed in `spikes/README.md` (open points).

### F14. Flowtable syntax and device names across versions

- nftables 1.0.6 and 1.1.3 accept the same multi-line declaration (`flowtable ft { hook ingress priority 0; devices = { lan, wana }; }`) and list it the same way (`hook ingress priority filter`, `devices = { lan, wana, wanb }`). Both reject a one-line `table inet a { flowtable ft { … } }` unless the inner block is followed by `;` or a newline.
- In the JSON listing, `dev` is a string for one device and an array for several (both versions); the FR-CT-2 check must accept both forms.
- Kernel 6.1 with nftables 1.0.6 rejects a flowtable that names a device that does not exist (`No such file or directory`). Kernel 7.1 with nftables 1.1.3 accepts it and attaches the flowtable hook when the device appears (`nft list hooks` after creating it). The check must compare names, including names of interfaces that do not exist yet (for example PPP interfaces), not only existing interfaces.
- The current nftables manual documents device names with a trailing `*` ("basic wildcard matching" on newer kernels). nftables 1.1.3 rejects unquoted `wan*` (syntax error) and treats quoted `"wan*"` as a literal name: on kernel 7.1 it hooks neither `wana` nor `wanb` (their packets are not offloaded). Wildcard support is therefore later than the newest version tested; the check should treat a trailing `*` as a prefix match when it appears in a listing (documentation only).

### Documentation cross-check (second round)

Checked against the nftables wiki and manual page (via Context7) and, where stated, kernel source v6.1:

- Flowtable fast path bypassing prerouting, forward and postrouting (wiki, "Flowtables", hook diagram): documentation-backed and confirmed (F13).
- "Flows are offloaded after the state is created" and the route of the other direction being "deducted from the packet that creates the flowtable entry", so that special `ip rule`s must match both directions (wiki): consistent with F13; with FTR the triggering packet carries the restored path mark, so both cached routes follow the path.
- "Devices are required for both traffic directions" (wiki): describes what full offload needs, but does not say that a single listed device still offloads one direction; the experiment shows it does (F13). Experiment wins: a flowtable without uplinks is not free of the bypass.
- Device names with a trailing `*` (manual: `DEVICE_NAME := string | string*`, "basic wildcard matching"): not supported by nftables 1.1.3 (F14).
- `meta pkttype` (wiki: broadcast, unicast/host, multicast): the documentation does not say that the type comes from the link layer, that tunnels report `host` for multicast and broadcast, or that locally generated packets are `host` in postrouting; established experimentally (F12).
- `ct direction original|reply` (wiki): behaves as documented (F11).
- Kernel source, v6.1: `nft_flow_offload_eval` requires a confirmed entry and an established TCP connection; `nft_flow_route` looks up the other direction with `flowi4_oif` set to the input interface and `flowi4_mark` set to the packet mark; `nf_flow_offload_ip_hook` tears the entry down when `nf_flow_dst_check` fails and does not read or write the packet mark; `ip_tunnel_rcv` calls `skb_scrub_packet`.

## Proposed amendments to SPEC.md

- **§4.7**: state that untracked packets are skipped in every chain and non-unicast packets in prerouting and postrouting (F2; the generator in `s2lib.sh` shows the rules); the policy rules end with `return`.
- **FR-FW-6**: other tables that read or write conntrack marks must use priorities above −200 (F3).
- **FR-REC-6**: the comparison normalises the JSON listing by removing `metainfo` and every `handle` (F9).
- **AS-15, AS-16, AS-27 and other rejection checks**: verify rejection by the absence of egress packets, because client-visible errors are rate-limited and can be lost (F7).
- **AS-30 / FR-SYS-2**: record that `src_valid_mark = 1` is what makes inbound port forwarding pass the IPv4 reverse-path check when no source rule covers the post-DNAT destination (F8).
- **AS-31**: the RELATED path MTU check can use an MTU bottleneck inside a provider with a full-size MSS advertised by the server, as in `t4` (F5).

- **FR-CT-2, §1.3, FR-FW-6, AS-33** (superseding the warning-only proposal first made here): flow offload, software or hardware, stays forbidden for traffic between downlinks and uplinks. Startup, online `check-config` and reload refuse a flowtable whose devices match a configured uplink or downlink (string and array `dev`, configured interfaces that do not exist yet, a trailing `*` treated as a possible prefix), in both firewall modes, with a diagnostic naming the flowtable, the selector and the interface; the documentation says that name checks do not cover stacked or bridged lower devices. During active operation every full reconciliation and every reload inspects the flowtables: a match against the running configuration logs an error and adds the degradation reason `flow_offload` while routing management continues; the reason clears only after a successful inspection finds no match. FR-FW-6 explains that FTR does not restore the packet mark of offloaded packets and that F13 is no general guarantee of offload compatibility. AS-33 covers the device forms, reloads, runtime detection and removal, failed inspection, coexistence with other degradation reasons, and a match only against a proposed configuration.
