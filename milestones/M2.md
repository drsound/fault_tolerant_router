# M2 — IPv6: points to close

Milestone M2 of SPEC.md §17: the IPv6 variants of the M1 scenarios where applicable, plus AS-12, AS-28, AS-35, AS-45(b) and AS-49; AS-45(a) remains the IPv4-only isolation scenario. The contract is SPEC.md v0.9. This file tracks what remains before M2 can be declared complete; it follows the layout of `milestones/M1.md`, which records how M1 was built and validated.

Status legend: **open** (not started), **partial** (implemented, not yet verified by the scenario or test named), **decision** (needs an agreement before work), **done**.

## Starting point

The M1 daemon is family-generic in most of its structure (layout, planner, reconciler, observer, nftables generation, FR-REC-9 family handoff), but every IPv6 path is refused by `Config::unsupported_features` ("IPv6 paths ([uplink.ipv6])"), at startup, on reload and by `check-config`. The M1 code paths that are IPv4-only by construction, or were never exercised with IPv6, are the first thing to inventory.

### DHCPv6 clients and NetworkManager (H4)

Experiments on the three environments (2026-10-04, kernel route lookups traced with the `fib6_table_lookup` tracepoint), kea announcing the server-unicast option at an address outside the uplink's on-link prefix:

| Client | Server-unicast option | Messages by unicast | Route lookup of a message by unicast |
|---|---|---|---|
| dhcpcd 10.1.0, 10.3.0 | honoured in manager mode only ("ignoring unicast option as not manager" otherwise) | Request and Renew | unbound: no source address, no interface; the kernel chooses the source after the lookup |
| ISC dhclient 4.4.3-P1 | honoured | Renew (the Request is multicast) | bound to the interface: the socket is bound to the link-local address, so the lookup is constrained to the interface with a link-local source |
| NetworkManager 1.52.1 (internal client) | ignored | none | — |

Under FTR, an unbound message by unicast is unbound router-originated traffic (INV-4): rejected while the active set is empty, balanced over it otherwise, possibly through another uplink. dhclient's Renew uses the balancing route of its own interface when that uplink is in the active set; otherwise the constrained lookup finds no route and is rejected, never sent through another interface. Messages by multicast (Solicit, Rebind, every message of NetworkManager) use the local table and are not affected. The AS-44 DHCPv6 scenario asserts these outcomes; the lease is always kept by Rebind at T2.

Not covered by the scenario: dhcpcd acquiring a lease while another uplink is in the active set. Its Request by unicast is balanced with a hash of fixed fields (no source address at the lookup, ports 546 and 547), so every retransmission takes the same uplink; when that is not the server's uplink, the acquisition never completes (a run with A and B in the active set, weights 100:1: ten Requests through A, no lease after 150 s, the provider dropping DHCPv6 from outside its access network). Third point for the specification review below.

NetworkManager with DHCPv6 prefix delegation, one-off run on virtual machines (2026-10-04): Debian 13, Linux 6.12, NetworkManager 1.52.1 managing two Ethernet uplinks, a provider with kea 2.6.3 delegating /60s and announcing the server-unicast option at an off-link address (renewal 30 s, rebinding 50 s, lifetimes 100 s), a second provider with Router Advertisements, and a dummy downstream interface with `ipv6.method = shared` (NetworkManager requests prefix delegation only for one). FTR (a release build of this branch, both families on both uplinks) was started with the uplinks deactivated, so with no lease, no global address, no default route and an empty active set; NetworkManager then activated the uplinks and the downstream interface. Within 5 s: DHCPv4 leases, the DHCPv6 address and a delegated /60 whose first /64 NetworkManager assigned to the downstream interface, Router Advertisement routes, both paths ready in both families. Renewals and rebindings, all by multicast, succeeded for three minutes, also with the delegating uplink out of the active set (its probes dropped). NetworkManager alternated Renew and Rebind every 30 s; a control run without FTR showed the same pattern, a behaviour of its client. FTR refused to start while systemd-networkd, which managed the management interface, had its foreign rule and route management enabled (FR-COEX-1), and ran once the drop-in its error message names was installed.

### Points for the specification review

- §4.1.1, IPv6 (and spike S1, `ip6_dst_lookup_tail`): after the failed first lookup of a socket bound to an interface, the kernel picks the source among all interfaces (the failed lookup has no device), not from the bound interface, before the second lookup. A connection bound to an interface whose path is outside the active set therefore goes through that path only when the chosen source is the interface's own address, and is rejected otherwise (AS-21: rejected through `ppp0`, `ENETUNREACH`); it never leaves through another interface. S1 saw the first case only. The text should state the condition; the guarantee that matters (never another interface) holds.
- FR-DISC-5: the kernel notifies neither the refresh nor the shortening of a Router Advertisement route's lifetime, nor its collection after expiry, and `RTM_NEWPREFIX` exists only for advertisements with prefix information (D6). FTR therefore tracks the expiry of each discovered route, re-reads its table at the expiry, and observes the advertisements themselves on a raw ICMPv6 socket (the receiving interface is the scope of the link-local source), re-reading the tables of that interface's advertised default routes. The text should state these kernel facts and the mechanism (§12.2 lists the Observer's sources), so that the one-second bound of FR-DISC-5 is seen to hold for lifetime changes too.
- FR-CT-5, DHCPv6 messages by unicast (server-unicast option, deprecated by RFC 9915): the exception of FR-CT-5 names only DHCPv4 renewals. dhcpcd sends its Request and Renew by unicast with an unbound route lookup, so they follow the balancing table like any unbound router-originated traffic: the Renew falls back to Rebind as in DHCPv4, but an acquisition while another uplink is in the active set can fail indefinitely (section "DHCPv6 clients and NetworkManager (H4)"), against "FTR MUST NOT prevent … DHCPv6 including prefix delegation". ISC dhclient binds its Renew to the interface; NetworkManager ignores the option (systemd-networkd, from whose DHCPv6 client NetworkManager's internal one derives, was not tested). The text should either state the exception for DHCPv6 with its consequence and the remedies (a server that does not send the option, dhcpcd outside manager mode, which ignores it, or a client that binds), or FTR should route these messages itself, which it cannot do without knowing which uplink each server belongs to.

## Simplification (2026-10-04)

Four reviews of the M2 code (reuse, simplification, efficiency, depth of the fixes; base `2656ef2`) applied before the external review. Daemon: a route notification is parsed once, and the re-reads it schedules are narrowed without losing a stale case (a replacement only when the view holds another route with the same destination and metric, a nexthop object's deletion only for the tables of the routes that use it, a Router Advertisement only for the tables of its default routes on that interface; an object no route uses no longer triggers a pass); the table is re-read after any failed route replacement, in both families; a re-read moves the dumped messages instead of cloning them and keeps only the previous expiries; the automatic gateway is resolved once per path and evaluation; the FR-SYS-3 diagnosis of the Router Advertisement settings is one function in `checks.rs`, shared by the startup warning and the 30 s warning, with a unit test; the injected faults of the test hooks are typed (the empty-table outcome is no longer parsed twice); one netlink attribute iterator serves extended acknowledgements and nexthop messages; one plan per pass when no path is new; a test hook shortens the 30 s warning delay for its scenario. Harness: `per_family!` generates the two tests of each family-generic scenario; fewer configuration builders, and per-path settings in `UplinkSpec` instead of string replacements in the generated configuration; shared helpers for flow continuity over several uplinks, IPv6 artifacts after a handback, refused startups, interface addresses, provider counters and server ports; `Uplink::families` removed (every uplink is dual-stack); readiness polling with three commands instead of twenty-four; one dnsmasq argument list for the providers and the PPP sessions. Not applied: dropping already expired routes from the view to remove the expiry watermark (it changes what the view mirrors), dropping the blackhole and FDB attributes of nexthop messages (kept with the kernel's attribute set of D5), coalescing the passes of queued notifications (older than M2, changes timing), family keyword methods and shared unit-test fixtures (more churn than value).
