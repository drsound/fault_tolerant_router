# M4 — Release: points to close

Milestone M4 of SPEC.md §17: packaging (with the example configuration of DIST-1, and the systemd readiness, reload and configuration exit status of IMPL-10 and §9), documentation, AS-34, repository transition, and the measurement of IMPL-9 on the integrated release build on a Raspberry Pi 4 with four uplinks. Also the points carried over from M3 and M2 (`milestones/M3.md`, sections "Carried over to M4" and "Carried over from M2"). The contract is SPEC.md v0.14 (v0.13 when the inventory was written). This file tracks what remains before 2.0.0 can be released; it follows the layout of `milestones/M2.md` and `milestones/M3.md`.

Status legend: **open** (not started), **partial** (implemented, not yet verified by the scenario or test named), **decision** (needs an agreement before work), **done**.

## Starting point

The daemon of `ab02acd` implements every functional requirement of SPEC v0.13 except the systemd integration of IMPL-10: it never reads `NOTIFY_SOCKET`, and `run` exits with status 1 for every failure (`main.rs`, `ExitCode::FAILURE`), including an invalid or untrusted configuration. `polywan reload` already reports an unknown outcome when the control socket's change closes its connection (`cli.rs:259-283`, `38c2327`) and exits with 1 for any answer other than 200, so also when the reload is not applied within 8 s (202). The example configuration is `config/example.toml` (two uplinks), embedded with `include_str!` (`config/mod.rs:328`) and printed by `generate-config`. There is no packaging: no unit file, no `sysusers.d` entry, no `.deb`, no man page, no release workflow; CI builds the static binaries of the three PLAT-3 targets, checks that they are statically linked and uploads them as workflow artifacts, and runs `cargo deny`; the version is `2.0.0-dev`. There is no `docs/` directory; the README describes 2.0 as unreleased, its status table lists M4 as planned and one bullet still says "Coming with M3". The harness starts the daemon directly in the router namespace (`testbed/src/inject.rs:231`, `Ns::spawn_env`), with per-run directories under `/run/polywan-tests` and `/var/lib/polywan-tests`, and the binaries from the build directory (`/root/ftr/bin` on the test hosts, the runner's home in CI). `tests/perf/impl9.sh` (M3, D16) measures CPU and RSS with four namespace uplinks. On GitHub (`drsound/polywan`, 184 stars) the default branch is `master` at `1ce8016`, which is also `legacy/ruby` and `v1-ruby-final`; `v2` descends from it (144 commits, a fast-forward); a stale `development` branch (2016) exists; the 11 open issues are exactly those named by DIST-5; the repository topics still name `iptables` (and `netwokring`).

The reviewer changed the proposals of 1, 3, 4 and 9, corrected an assumption about msmtp's AppArmor profile (disabled by default, from the package sources), and found what became D5, D6, P8, H7 and parts of P1, P3, H2, H4 and M1. The consequences are part of the items above.

1. Exit status 78 (§9): a configuration that cannot be read, parsed or validated, an FR-CFG-5 failure, an absent or prohibited account, a conflict with the manifest's structural settings or uplink identities; other failures that end startup exit 1, account lookup errors and fatal state-file errors of IMPL-6 included (an unreadable health checkpoint stays a warning) (D2).

8. Only msmtp documented and tested; queueing recipes and other mail systems in §13 (W6, DIST-3).
9. `After=nftables.service network.target`, not before `network-pre.target`: starting earlier would skip the networkd compatibility check at boot (P1).
