# M3 — Operations: points to close

Milestone M3 of SPEC.md §17: API and remaining CLI, drain, policies, events, email, hooks, metrics, quality gates. Scenarios: AS-06, 07, 15, 16, 25, 39, 46, 48 and 51, the email variants of AS-20, and the drain and policy variants of AS-09, AS-27, AS-29 and AS-42. The contract is SPEC.md v0.12 (v0.11 when the inventory was written). This file tracks what remains before M3 can be declared complete; it follows the layout of `milestones/M1.md` and `milestones/M2.md`.

Status legend: **open** (not started), **partial** (implemented, not yet verified by the scenario or test named), **decision** (needs an agreement before work), **done**.

## Starting point

The configuration of every M3 area is parsed and validated (`config/raw.rs`, `config/validate.rs`: policies, `[notify.email]`, `[[notify.hook]]` with event filters, `[api]`, `[metrics]`, `health.quality` with its per-uplink merge), but the daemon refuses policies, email, hooks, `metrics.listen` and quality gates through `Config::unsupported_features`, at startup, on reload and in `check-config`. Parts of the routing side exist: the planner already installs the policy-balance and policy-block lookup rules, tables and guard of every uplink and drops a drained path's policy routes; selection excludes drained paths; `state.rs` reads and writes `drain.json` atomically, but nothing in the daemon writes it. The prober can run attempts to completion (`run_to_completion`, set when gates are enabled) and the health machine knows `Round::Degraded`, but nothing computes loss, RTT or jitter. Not present: the API socket and its HTTP server, the CLI commands that use it, the event bus and its ring, SMTP, hook processes, metrics, and the nftables matching of policies. The status `degraded`, its reasons and the FR-EV-1 events exist only as log lines, which the harness reads (`Polywan::log`, `Polywan::wait_log`).

### Open questions

Settled on 2026-10-04 as SPEC v0.12, agreed with the external reviewer in two rounds (the reviewer disagreed with the first proposals of 1 and 6, and their texts were adopted). The implementation consequences are part of the items above.

1. IMPL-4 and the M1 design (D4): the nftables transaction and write-ahead manifest writes keep their order before the mutations that depend on them, but waiting for them MUST NOT suspend the State task's processing of discovery, probe results and routing deadlines; independent health decisions and withdrawals continue within FR-HEALTH-5. Completions carry operation and generation identity; obsolete ones activate nothing; a timeout does not cancel a started write. Blocking file, sysctl and identity work, subprocess spawning and supervision run outside the routing executor. Design: State, observer and probers on the current-thread runtime of the main thread; API, metrics, notifiers and subprocess supervision on a second current-thread runtime in its own thread; the in-flight nft step treated like a step not yet succeeded (its dependants are not attempted), so later passes can withdraw. Tests: slow nft and slow persistence overlapping a carrier loss.
2. Corrupt or unknown-version manifest or drain state fails startup unless `--reset-state`; other drain read errors fail startup; an unreadable health checkpoint is ignored with a warning (cold start); validation precedes manifest and routing mutations; drain intent of removed uplinks pruned durably at startup and on reload (after preparation, before commit; a failed write rejects the reload). Implemented right after D1: drain state read and pruned before the manifest write, `DrainState` written with the supported version, the dry run honours drain, scenario `impl6_unreadable_state_and_drain_pruning` (`tests/m3.rs`).
3. Policies only in the original direction (`ct direction original`, §4.7 step 1.3); AS-15 gains a matching downlink reply of an unassigned connection (D2, H6).
4. Quality window (D3): statistics computed and published with or without gates (documented bias without them); cleared when the probing generation changes or the path stops being ready, not when health goes `down`; a smaller window drops the oldest rounds, a larger one grows prospectively; new thresholds apply at the next round; a statistic without inputs is unavailable, not zero.
5. `nix` (features `user`, `signal`, `fs`, `process`) is named by IMPL-2; account lookups through libc outside the routing executor; documentation requires local hook users and API groups (musl may consult nscd).
6. Metrics listener: prepared before commit, a bind failure rejects the reload, connections closed on change (FR-MET-1). Sockets: a socket is replaced only if created by this instance or identified by protected ownership metadata (planned: a root-only record of published path, device and inode in the lock's runtime directory); otherwise the administrator removes it; unlink at shutdown only if device and inode still match (FR-API-1).
7. `notify.email.events` with a default selection; Subject `PolyWAN notification`, `PolyWAN notifications suppressed`, `PolyWAN notification test`, with ` (HOST)` for a valid host name; limits: event queue 256 events and 1 MiB, batch 200 changes and 64 KiB, body 128 KiB, encoded message 512 KiB, at most 8 waiting messages and 4 MiB (FR-MAIL-1, FR-MAIL-2).
8. IMPL-9 is measured in M4 on the owner's Raspberry Pi 4 (network namespaces allowed) and is a release criterion; M3 records an x86_64 smoke measurement (D16).
9. `netlink-sys` and `socket2` sockets are close-on-exec, but descriptors the daemon itself inherited may not be: mark descriptors above 2 close-on-exec before any subprocess spawn, `notify-test --offline` included (D10). tokio's orphan reaping is best effort: supervision awaits each direct child and keeps its runtime running through cleanup. Each `numgen` expression has its own counter (Linux 6.1 source); H4 still verifies the generated rules.
